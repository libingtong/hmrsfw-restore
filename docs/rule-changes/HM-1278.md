### 1. 共同的起因：Playwright 时钟一个真实宏任务只跑一个到期定时器

`runPage` 用 `page.clock.setSystemTime` 让两侧从 HAR 录制那一分钟开始走（HM-1021）。Playwright 1.64 的时钟因此接管了页面的 `setTimeout` / `setInterval` / `requestAnimationFrame`：它在 `_runTo` 里按到期顺序逐个执行到期的定时器，每执行一个就 `await` 一次真实的 `setTimeout`（`node_modules/playwright-core/lib/coreBundle.js` 的 `_callFirstTimer`）。

还原版表单页加载时有几十个同时到期的 10 ms 定时器（ant-design-vue Input 每个输入框一个 `function(){e.value=t.value}`），每个都触发一次整页重渲染。读回放中页面时钟内部状态（`window.__pwClock.controller`，`page.uc.personLoan.detailInfo`，还原侧）：

| 真实时间 | 队列里的定时器 | 已到期未执行 | 上传列表 `appear-prepare` 元素 |
| --- | --- | --- | --- |
| 0.5 s | 42 | 28 | 3 |
| 2.6 s | 24 | 10 | 3 |
| 4.6 s | 12 | 5 | 3 |
| 5.6 s | 10 | 0 | 0 |

积压期间页面里任何新排的定时器（包括门槛自己的）都排在这几十个后面，要等几秒才执行；而 DOM 的文字长度和元素数不变，门槛的稳定判据看不出来。不装时钟时同一页 4/4 次都立即走完。原版侧同样受影响，只是轻得多（旧基线就是这样截到半途状态的，见第 3 节 zcyz）。

### 2. 规则 1 `toast-read-real-timer`：toast 文字用原生定时器读

记录器在 toast 节点出现时排一个 `setTimeout(50)` 读 `innerText`。这个定时器是页面的（被时钟接管），积压时排在队尾：

- `page.uc.sign.corpInfo` 还原侧，旧记录器，同一 dist 连续 4 次：toast 节点在 2.2–12 s 出现，3 次到截取（约 6 s）时读文字的定时器还没执行，记录为空；不装时钟 4/4 记到。
- `page.uc.collage.studentInfo`：toast 在 3.9 s 出现，50 ms 的读在 7.4 s 才执行。
- 页面本身每次都弹出了 `请求地址出错: <url>`（与原版一致）：对照页 `page.uc.collage.nojob`、`page.uc.sign.corpApply` 是同一个 404 接口、同一个拦截器，碰巧不积压，一直通过。

改法：初始化脚本先于时钟安装执行（实测：init 脚本里 `setTimeout` 是原生的，导航后被替换），在那里取下原生 `setTimeout`，读文字用它；`__pwClock.builtins.setTimeout` 是时钟自己保存的原生函数，作为另一种加载顺序的兜底。读的时机（出现后 50 ms）、读法、记录的阶段都不变。

修改后（同一 dist、同一基线）：studentInfo、corpInfo、uc.404 还原侧各 4 次，toast 12/12 记到；原版侧（legacy-dist）studentInfo 3/3、zcyz 3/3 记到。

### 3. 规则 2 `settle-replay-clock`：页面定时器积压时不算稳定

`page.uc.personLoan.detailInfo`、`page.uc.CorpAttestationapprove` 的 `load.html` 差异只在上传列表：还原侧截到

```
<div class="ant-upload-list-picture-card-container ant-upload-animate-inline ant-upload-animate-inline-appear ant-upload-animate-inline-enter ant-upload-animate-inline-appear-prepare ant-upload-animate-inline-enter-prepare" style="height: 20px; opacity: 1;">
```

原版基线是动画结束后的 `<div class="ant-upload-list-picture-card-container">`。两侧都是 ant-design-vue 上传列表的出场动画：装时钟时两侧都要 4–8 s 才离开 `appear-prepare`（上表），不装时钟时两侧都立即结束。门槛在 3 s 左右判为稳定（文字和元素数不变）就截了。

改法：`waitStable` 每次轮询时在页面里排一个 0 ms 的 `setTimeout`（页面的，时钟按到期顺序排在积压之后），用原生 `performance.now` 计它多久执行，500 ms 内没执行就算这一轮有变化。无积压时时钟每 100 ms 推进一次，探针在 100 ms 内执行，判据与原来相同。没有改 `STABLE` 的任何时长，最多仍等 30 s。

先试过两种不成立的做法，记在这里免得复核时重走：页面里的心跳 `setInterval`（积压期间时钟把心跳穿插在积压的定时器中间执行，量不出积压）；比较页面时间和真实时间（页面读 `performance.now()` 时时钟会同步到真实时间，二者始终一致）。

修改后（同一 dist、同一基线，各 2 次）：personLoan.detailInfo 2/2、CorpAttestationapprove 2/2 通过，像素差 0。代价：这类重表单页的稳定等待从约 3 s 变成 8–22 s（CorpAttestationapprove 最长 22.5 s），仍在 30 s 上限内；轻页面不变（2.5–3.2 s）。

旧基线里同样有被截在半途的原版：`page.uc.zcyzCorpAttestationapprove` 的基线（10-19）两次运行都是 `ant-upload-animate-inline-appear-active`、`height: 160px`，也都没记到外壳字典请求返回的「操作失败」toast（HAR 第 2 条 `getDictItemsByCode` 无 `dictCode`，`success:false, message:"操作失败"`）。用本分支重录的临时基线（`baseline.mjs --out`，同一 HAR）两次都是动画结束态、都有「操作失败」，还原版对它 2/2 通过。用当前 `main` 在机器不忙时重录也是如此（4/4），所以这页另行 `rerecord`，不依赖本分支。

### 4. 规则 3 `final-rootless-both`：两侧都没有交互后的根是同一状态

`page.portal.resumeAnalysisReport.resumeAnalysisReport` 报 `final.root: no original root candidate with class null (restored final root)`。交互脚本最后一步点 `.ant-modal-close` 关掉「正在生成报告中…」弹窗（原 chunk `legacy-dist/portal/assets/resumeAnalysisReport.1783320636200.js:4:2974` 起 `onMounted` 里 `setTimeout(()=>{e.loadingModal=!0},500)`）。之后原版 `main > *` 和还原版 `#poc-main > *` 都没有任何根候选：同一 dist 和 legacy-dist 各回放一次，`final.candidates` 两侧都是 0 个；原版基线两次运行也都是 0 个。

`compare.mjs` 里还原侧的根取第一个候选（`cls` 未指定时 `fFound` 恒为真），没有候选也算「找到了，class 为 null」；原版侧按 class null 找不到，`noRoot` 就报失败。两侧状态相同，却判为不同。

改法：只在 final 阶段、且还原版和**原版每一次运行**都没有任何根候选时，不报 `final.root`；此时 final 的 html / text 两侧都不比（原版为 null，原有逻辑跳过）。只要任何一侧有候选（包括原版有布局的其他元素、只有一次原版运行没有根），都照旧报 `final.root` 或比内容（用例里逐一列出）。load 阶段不变。

页面加载时报的 `Cannot read properties of null (reading 'isCurriculumVitae')` 是原代码自身行为（同文件 `4:1802`：`Jt(...).then(a=>{e.isCurriculumVitae=a.result.isCurriculumVitae})` 未判空），原版基线两次运行有同一条报错，不是还原问题。

修改后：resumeAnalysisReport 2/2 通过。
