## HM-1382：规则变更 rule/hm-342-offscope-all 全量回归失败 3 页的根因分析——与该规则无关，是 orderFiles 的工单归属 bug

- 分支：`hm-1382/order-files-sibling-target`（基于 `main`），每条规则一个提交：
  1. `rule(check): order-files-sibling-target`：`tools/sfc-util.mjs` 的 `orderFiles` 跳过另一张工单自己的 `target`；新增 `tools/test/order-files.test.mjs`；
  2. 本文。
- 触发单：HM-1382（incident，裁定员）——`rule/hm-342-offscope-all` 合入 main（`02292cc`）后，任务 `01a15320-430f-7ab4-aa4c-cf4f6fd9947e`（purpose=rule-regression）的全量回归在 `page.uc.CorpAttestation`、`page.uc.personLoan`、`page.uc.zcyzCorpAttestationapprove` 上失败，自动回退与某条后续提交冲突（`why:"conflict"`），未执行，排障单交给裁定员判断失败页是否由该规则引起（HM-1276 的既有流程）。
- 不动的东西：
  - `rule/hm-342-offscope-all` 本身（判定：与这三页的失败都无关，原样留在 `main`，不回退）；
  - 像素阈值、HTML/请求判据、HAR、基线、公共库清单、`package.json`；
  - `orderFiles` 对正常情形（一张工单自己 target 之外、不属于任何其它工单的子组件）的行为不变。

### 0. 判定：三页的失败都与 `rule/hm-342-offscope-all` 无关

`tools/baseline.mjs` 里 `offscopeFixed`/`offscopeAll` 两个标记只在 `wo.recordVia` 为真时才写（见该文件 `...(wo.recordVia ? { offscopeFixed: true, offscopeAll: true } : {})`），`tools/gate/replay.mjs` 的 `markOffscope` 只在 `runPage` 的 `opts.componentScope` 存在时才生效（`COMPONENT_SCOPE.set(page, opts.componentScope)`，仅 recordVia 页面会设置）。`queue/page.uc.CorpAttestation.json`、`queue/page.uc.personLoan.json`、`queue/page.uc.zcyzCorpAttestationapprove.json` 三者都没有 `recordVia` 字段——这条规则改的比对路径，这三页从未经过。回退没有执行到也不影响这三页的结果：真正的根因在别处，按页分列：

### 1. `page.uc.personLoan`：`orderFiles` 把子路由自己的 target 当成了本工单的交付物

门槛报告（任务 `01a15320` 的 `gate.1`，`$RESTORE_STATE/gate/runs/aa7059b5994232f1/pages/page.uc.personLoan/result.json`）：

```json
{"check":"components","where":"apps/uc/src/views/personLoan/","hint":"原 chunk 定义了 1 个组件（index），还原版交付了 2 个 .vue。不要拆出原包里没有的组件"},
{"check":"text-nodes","where":"apps/uc/src/views/personLoan/detailInfo.vue","hint":"多出文本 \"上传本人照片\"：……"}（共 11 条，全部 where 都是 detailInfo.vue）,
{"check":"branches","where":"apps/uc/src/views/personLoan.vue","hint":"没有 v-else 的 v-if 分支数不一致：原 render 有 4 处，还原版有 11 处"}
```

证据：

- `queue/page.uc.personLoan.json`：`target=apps/uc/src/views/personLoan.vue`，`subComponentDir=apps/uc/src/views/personLoan/`，`sourceChunk=legacy-dist/usercenter/assets/index.175161560754513.js`，`components=[{"name":"index","scopeId":"data-v-5e61620f"}]`（原 chunk 只定义 1 个组件）。
- `queue/page.uc.personLoan.detailInfo.json`：`target=apps/uc/src/views/personLoan/detailInfo.vue`，`sourceChunk=legacy-dist/usercenter/assets/detailInfo.1751615607545.js`，`components=[{"name":"detailInfo","scopeId":"data-v-c8cdaf6d"}]`，路由 `/personLoan/detailInfo`——与 personLoan 是两张独立工单：不同 chunk、不同 scopeId、各自独立的路由，不是 personLoan 的子组件。detailInfo 只是物理上落在 personLoan 的 `subComponentDir` 目录里（因为它是 `/personLoan` 下的子路由）。
- `tools/sfc-util.mjs`（改前）的 `orderFiles`：`if (order.subComponentDir) for (const f of walk(abs(order.subComponentDir))) files.add(f);`——不分辨这个文件是不是另一张工单自己的 target，把 `personLoan/detailInfo.vue` 原样并入 personLoan 的文件集合。
- `check-text-nodes.mjs`：`orig` 只读本工单 `sourceChunk`（personLoan 的 index chunk）的文本，`restored` 读 `orderFiles` 返回的全部文件（因为上面的 bug，混入了 detailInfo.vue）的文本，两边做差集——detailInfo.vue 里合法的文本自然不在 personLoan 的 chunk 里，被判成『多出』。实测：

  ```
  $ grep -c "上传本人照片\|上传人像面\|上传国徽面\|上传营业执照\|基本信息\|贷款信息\|就业创业信息\|图片信息\|阅读并同意《办理须知》" legacy-dist/usercenter/assets/detailInfo.1751615607545.js
  1   # 一行压缩代码，这些文本都在
  $ grep -c "上传本人照片" legacy-dist/usercenter/assets/index.175161560754513.js
  0   # personLoan 自己的 chunk 里一个都没有
  ```

  11 条『多出文本』逐一核对：全部是 detailInfo 原 chunk 里本就有的静态文本，personLoan 自己的 chunk 里从未出现过——不是 detailInfo.vue 写错了，是被拿去跟不相关的 chunk 比对。
- `check-directives.mjs` 同理：`branches` 累加 `orderFiles` 返回的全部文件的 v-if 分支数（`files = orderFiles(order, APP)`），detailInfo.vue 自己的分支被计入 personLoan 名下，报告却打在 `order.target`（personLoan.vue）上，制造出『personLoan.vue 11 处分支，原 chunk 只有 4 处』的假象。
- `check-components.mjs`：`vue.length` 数的是 `orderFiles` 返回集合里 `.vue` 文件数，personLoan 自己只应有 1 个（`target`），混入 detailInfo.vue 后变成 2 个，对不上 `expected.length=1`。

**范围不止这一页**：同样『子路由的 target 落在父页面 subComponentDir 里』的目录重叠还有三处（`node -e` 扫描 `queue/*.json` 的 `subComponentDir` 与其它工单 `target` 的前缀关系）：

| 父工单 | subComponentDir | 子路由工单 | target |
| --- | --- | --- | --- |
| `page.uc.corpLoan` | `apps/uc/src/views/corpLoan/` | `page.uc.corpLoan.corpLoanInfo` | `apps/uc/src/views/corpLoan/corpLoanInfo.vue` |
| `page.uc.oddjob.lack` | `apps/uc/src/views/oddjob/lack/` | `page.uc.oddjob.lack.add` | `apps/uc/src/views/oddjob/lack/add.vue` |
| `page.uc.oddjob.need` | `apps/uc/src/views/oddjob/need/` | `page.uc.oddjob.need.add` | `apps/uc/src/views/oddjob/need/add.vue` |

这三组目前恰好没有触发失败（文本/分支数凑巧没撞上，或还没被一次全量回归同时测到），但 bug 的触发条件（父工单 `subComponentDir` 物理包含子路由工单的 `target`）完全相同，修复按同一条规则一并生效，不单独为某一页改。

### 2. `page.uc.CorpAttestation`、`page.uc.zcyzCorpAttestationapprove`：上传列表 HTML 差异，证据不足，未写规则

两页都在浏览器阶段的 `html`/`pixel` 检查上失败，差异都落在 `span.ant-upload-picture-card-wrapper > div.ant-upload-list` 内（长度各差 92 字节）。`rule/hm-251-record-via-root` 的排障单 HM-1363（`docs/rule-changes/HM-1363.md` 第 2 节）在这两页上预告过一个尚未归一化的残留：『+上传』触发按钮的 `collapseMotion` leave 过渡——原版两次回放都停在过渡中途（带 `-leave-from`/`-leave` 类和行内 `height`），还原版两次都已经是过渡结束的样子，语义等价但未写成规则，因为『没有拿到足够把握的证据』，留了一句『如果这一点仍然导致失败，再开排障单单独处理（可能需要在浏览器里实测）』。

这次本可能就是那张预告的排障单，但本次门槛运行只保留了 `result.json` 的摘要（`offset`/`lengths`），原始的 `orig`/`rest` `load.html` 没有留存（HM-876/HM-1270 的 slimResult），拿不到逐字证据去确认这 92 字节差异就是 HM-1363 §2 的残留而非别的差异；也没有可用的浏览器实测环境去补这个证据（本机没有现成的 Playwright 复核流程可在这次排障单的时间窗口内跑完）。按硬规则『不要为了让某一页通过而登记已知差异或改规则；必须有原 chunk 中的证据』，证据不够就不写规则。

**处理**：不回退 `rule/hm-342-offscope-all`（与它无关，上面已证）；这两页本身不需要 `rerecord`（基线没问题）；比对规则的残留问题保持 HM-1363 §2 的结论——下一次全量回归命中同样的差异时，留存一次完整的门槛 diff（或在那次排障单里现跑一次 `--keep` 的门槛）再决定要不要写第四条规则，不在本单勉强补。

### 3. 为什么不算放宽

- `orderFiles` 的改动不改变任何比对判据，只改变『这个文件算谁的』：一张工单自己的 `target`、自己 `subComponentDir` 下不属于任何其它工单 `target` 的文件，一个不少地照常比对；唯一跳过的是『physically 落在这张工单目录里、但明确是另一张工单自己 `target` 的文件』——有两张工单各自独立的 `queue/*.json`（不同 `sourceChunk`、不同 `scopeId`、不同路由）作证据，不是猜的。
- 范围封闭：只在 `order.subComponentDir` 的遍历结果里按『是否是别的工单的 target』过滤，不碰 BFS 从 `target` 出发按 `.vue` 相对导入收集到的文件（那些文件确实是本工单引用的，无论物理位置在哪）。
- `page.uc.CorpAttestation`/`page.uc.zcyzCorpAttestationapprove` 没有写规则：证据不足就不写，不勉强让它们『过』。
