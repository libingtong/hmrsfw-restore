## HM-49：分段单的静态自检误判（check-components 非末段条件、segments 区间起点、片段的相对导入）

- 分支：`rule/hm-49-segment-gate`（基于 `main` `3770f86`），四个提交，每条一个：
  1. `rule(check-components)`：非末段只在本段包含整页主组件时才要求 `target` 存在（A1）；
  2. `rule(segments)`：组件区间从上一个组件的定义结束处起算；分段的 text-nodes / directives / branches 原版一侧改按 `factRanges` 取（A2 起点）；
  3. `docs(work-orders)`：`range` 的单位写明是 JS 字符串下标，不是字节（A2 单位，只改文档和工单说明文字）；
  4. `rule(check-imports)`：`_seg/` 片段的相对导入按合成后文件的目录解析；分段单的「本页文件」是整页的文件（第 3 项前半）。
- `queue/` 用 hmrsfw-vue `6e95728`（`main` 上现有 queue 的生成基础）重新生成；在本分支上再生成一次没有差异。
- 提出：裁定员；复核：两个非 Anthropic 家族的复核员。
- 来源：`docs/rule-changes/HM-46-findings.md` 第 A 节，`restore/fast-lane` 的 `tools/fast-lane/results/S1.json` notes 第 3～6 条。

下文偏移都是 JS 字符串下标（见第 3 条）。

### 1. check-components：非末段的 target 条件（A1）

改动前（`tools/check-components.mjs:16-17`）：

```js
const expected = order.type === "segment" && !order.assemble ? order.components : order.components ?? [];
if (order.target && !existsSync(...) && (order.type !== "segment" || order.assemble || expected.some((c) => c.name === order.components?.at?.(-1)?.name)))
```

非末段时 `expected` 就是 `order.components`，`expected.some(c => c.name === order.components.at(-1).name)` 只要本段有组件就成立。改为与页面单（`order.page`）的主组件 `components.at(-1)` 比较。

**为什么是修正误判**：分段单的 `target` 是整页主组件的文件。主组件在 chunk 末尾（`segments.mjs` 第 1 条规则），要么整组件落在最后一段，要么拆成 script / template 两部分，由最后一段的 `assemble-segments.mjs` 合成到 `target`。非末段从来不交付 `target`（看 `outputs`：`seg.uc.zcyzCorpAttestationapprove.1` 只有 `zcyzCorpAttestationapprove/BusinessModal.vue`）。原条件要求非末段交付一个不归它交付的文件。

**没有放宽**：
- 末段（`assemble: true`）和页面单照旧要求 `target`；
- 非末段如果真的含主组件，照旧要求（测试里构造的反例仍失败）；
- 非末段自己的 `outputs` 逐个检查存在，这一段没动。

### 2. segments：组件区间的起点（A2）

Vue 编译一个带 scoped 样式的 SFC 时，会在组件定义**之前**输出这个 SFC 自己的模块级代码：`_withScopeId` 包装（`n => (pushScopeId("data-v-<本组件>"), n = n(), popScopeId(), n)`）、被提升的静态 vnode、常量 props。改动前，`componentRegions()` 从含 `__name` 的语句起算，这些代码就落进了**上一个**组件的区间。

原 chunk 证据：

| chunk | 位置 | 内容 | 属于 |
| --- | --- | --- | --- |
| `legacy-dist/usercenter/assets/index.175161560754523.js`（`page.uc.gongfuWorkshop.positionPosting`） | @12790 | `const Je=Z(Ge,[["__scopeId","data-v-2b6ba6e8"]])` | 上一个组件 `workShopBaseInfoModel` 的 `_export_sfc` 包装 |
| 同上 | @12839 | `te=i=>(fe("data-v-4378db7d"),i=i(),me(),i)` | `workPositionAddOrEditModel`（`componentsOfChunk`：`data-v-4378db7d`） |
| 同上 | @12905 | `je=te(()=>k("span",null,"元/月",-1))` 等 3 个提升 vnode | 同上 |
| 同上 | @13143 | `to=G({__name:"workPositionAddOrEditModel",…` | 改动前该组件区间的起点 |
| `legacy-dist/usercenter/assets/zcyzCorpAttestationapprove.1751615607545.js` | @14572 | `j=k=>(Ze("data-v-e472039d"),k=k(),Xe(),k)` | 主组件 `zcyzCorpAttestationapprove`（`data-v-e472039d`） |
| 同上 | @15012 起 | `j(()=>f("div",…,"上传人像面",-1))` 等 | 同上 |
| 同上 | @15621 | `ut=Je({__name:"zcyzCorpAttestationapprove",…` | 改动前该组件区间的起点 |

改动：
- 组件 i 的区间从组件 i-1 的定义（声明符 / 逗号表达式的一项 / 语句）结束处起算，到自己的定义结束处为止；最后一个组件到 chunk 末尾。区间仍然首尾相接、覆盖整个 chunk。上一个组件的 `_export_sfc(...)` 包装（不含渲染调用）落进下一个区间，`kb` 相差几十字节。
- 分段新增 `factRanges`：本段要还原的渲染调用所在的区间。整组件取整个区间；`template` 部分取「定义之前的提升代码 + 渲染函数」；`script` 部分为空（片段是 `<script setup>` 代码，不含模板；整页的检查在末段合成后照常进行）。`check-text-nodes`、`check-directives`（含 branches）原版一侧按 `factRanges` 取，没有该字段的旧工单退回 `range`。

**为什么是修正误判**：提升的 vnode 是被 `pushScopeId("data-v-<X>")` 包住、只被组件 X 的渲染函数引用的模板内容，就是组件 X `<template>` 里的静态节点。按 SFC 写，它只能出现在 X 的 `.vue` 里。改动前它被算给上一段，于是：
- 上一段被要求交出别的组件的文本（误报）；
- 真正还原 X 的那一段反而看不到这些文本（漏检，只能等末段整页检查兜底）。

**没有放宽**：
- 原版一侧的文本总数不变，只是换了归属：每段的 `factRanges` 首尾相接，合起来覆盖全部组件区间；script 部分的区间只在合成后的整页检查里算；
- 末段对整页的检查（`range: null`）不受影响，回归里已合成页面的末段结果前后一致；
- 21 张分段单的组件和片段归属（`components` / `parts` / `outputs`）全部不变，变的只是 `range`、`kb`、`factRanges` 和说明文字。

反例（hmrsfw-vue `fast-lane-blocked/S1` 的片段状态，见下文「验证」）：把 `seg.uc.collage.studentApply.1` 交付的 `studentApply/cpyInfo.vue` 里的「基本信息」改成「基本资料」，改动后的 self-check 报「缺少文本 "基本信息"」和「多出文本 "基本资料"」两条，正好是这处改动。改动前同一检查报 61 条，其中 59 条是主组件的提升文本（「就业协议合同」「毕业生信息」…）。单元测试另覆盖：`workPositionAddOrEditModel` 的包装函数在自己区间内、不在上一区间内；script-only 分段的 `factRanges` 为空；template 部分的 `factRanges` 以 `[start, def]` 开头。

### 3. `range` 的单位（A2）

`range` 来自 Babel 的 `node.start/end`，是 JS 字符串下标（UTF-16 码元）。`docs/work-orders.md` 和工单 `instructions` 原来写「字节区间」。7 个用户中心分段页的 chunk 含中文，字符数和字节数不同（表见 `HM-46-findings.md`）。

处理：**改文档，不改代码**。`segments.mjs`、`check-text-nodes`、`check-directives` 都对 `chunkSource()` 返回的同一个字符串取下标，内部一致；改成字节偏移要在每个使用者处换算，收益为零。改动：`docs/work-orders.md` 的 `range` 一行、`tools/work-orders.mjs` 生成的说明（「字符区间 [a, b)（JS 字符串下标，不是字节偏移；…）」），`segments.mjs` 文件头加了一行说明。门槛判据不变。

### 4. check-imports：`_seg/` 片段的相对导入（第 3 项前半）

`assemble-segments.mjs` 把 `_seg/<组件>.script.ts` 原样贴进合成后的 SFC（主组件 → `target`，其余 → `<subComponentDir><组件>.vue`）。所以片段里的相对导入只能按合成后文件的位置写。改动前，规则 1 按片段自己的目录（`_seg/`）解析：
- 按合成后位置写的正确导入报「找不到文件」（实例：`seg.uc.zcyzCorpAttestationapprove.2` 的 `import BusinessModal from "./zcyzCorpAttestationapprove/BusinessModal.vue"`；合成后的 `apps/uc/src/views/zcyzCorpAttestationapprove.vue:965` 是同一行，S1 记录该页 vite build 通过）；
- 反过来，按 `_seg/` 写、合成后会断掉的导入，改动前能通过解析。

另外，分段单的 `files` 只有本段的 `outputs`，同页其他段交付的组件文件（如第 1 段的 `BusinessModal.vue`）不算「本页文件」。即使目录算对了，也会报「不在本页目录内」；分段并行时还取决于兄弟段有没有先合入。

改动：
- `<subComponentDir>_seg/<组件>.script.ts` 的相对导入从「合成后文件的目录」解析；其他文件不变；
- 分段单的本页文件 = 页面单的本页文件（`orderFiles(page)`：`target` 和 `subComponentDir` 下的 `.vue`），加上页面每个组件合成后的文件。这和规则 4 的 `mine()` 对分段单已经允许的范围一致（`target` 和 `subComponentDir`）。

**没有放宽**：只能导入页面自己的组件文件；名字不对、目录不对、别的页面，照旧失败。测试里的反例（片段同目录写法 `./BusinessModal.vue`、用 `../` 绕回 `../zcyzCorpAttestationapprove/BusinessModal.vue`、不存在的组件 `./zcyzCorpAttestationapprove/Nope.vue`、另一页的 `./CorpAttestation.vue`）改动后都报失败。`main` 刚合入的 HM-26 改动（`subComponentDir` 下的非代码文件）不受影响，本分支在它之上，变基没有冲突。

### 判定不改的一项：`css-by-scope <id> --write`（第 3 项后半）

同页其他段的组件文件还不存在时，`--write` 拒写。`css-by-scope` 不判通过与否，它是还原员写 `<style>` 的工具，不属于门槛规则，不放进规则变更。现有绕法：非末段用 `--chunk/--css`，或库函数 `planStyles` / `writeStyles` 只写本段的 scopeId；末段合成后对整页运行 `--write`。要改，应按工具缺陷另开单。
