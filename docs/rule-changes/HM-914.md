  2. 本文。
- 快速通道：`rule/hm-914-fast-lane`（基于 `restore/fast-lane` `76b7e9b`，第 1 个提交 cherry-pick 为 `44c221e`）。`baseline.mjs` 有冲突，因为 fast-lane 没有 coverage 参数，按 fast-lane 的上下文手工合并，只加了 `interactRef` 一项。合入 `main` 后再合入 `restore/fast-lane`，做法同 HM-380。
- 提出：裁定员；复核：两个非 Anthropic 家族的复核员。
- 来源：集成回归单 HM-866、870、873、880、896 都报 120~140 页「没有可用基线」，绝大多数原因是 `interaction script changed since the baseline`。
- 不动的东西：比对和归一化规则（`rules/compare/`）、像素阈值、请求判据、基线、HAR、公共库清单、page 模式。

### 1. 根因：脚本没变，是门槛读错了地方

- `baselineFor`（`tools/gate.mjs`）拿 `interactScript(wo.id)` 的 SHA-256 和基线里的 `b.script` 比。`interactScript`（`tools/gate/common.mjs`）只读门槛自己检出目录（`ROOT`）下的 `tests/interact/<id>.json`；读不到就退回 POC 的 `interact-scripts.mjs`，再读不到就是 `null`。
- 录制员的 `record-page.mjs` 先在本地写好脚本、录基线，再用 `commitToIntegration`（`tools/record-lib.mjs`）把脚本**只提交到工具仓库 `integration` 分支**。所以基线里的 `b.script` 是 integration 分支上那份脚本的 hash。
- 工具仓库各分支上的脚本数：`main` 8 份、`restore/fast-lane` 8 份（都是 POC 的 c02…c19，三条分支上逐字节相同），`integration` 193 份。门槛员从 `main` 或 fast-lane 跑集成回归时，绝大多数页读不到脚本，读成 `null`，hash 自然对不上。还原版回放时也是按 `null` 跑，交互步骤根本没执行。
- 旁证：HM-857、HM-863 的门槛员按 HM-848 手动把 integration 的 `tests/interact` 拿到检出目录后重跑，「script changed」从 117/118 页降到 0，只剩 3 页没有基线。

### 2. 改动

- **集成模式（`--mode integration`、`--regress`）**：门槛开跑前，把工具仓库的 `integration` 分支 fetch 到一个私有 ref（`refs/gate-interact/<pid>-<时间>`），解析出提交号后删掉这个 ref。用私有 ref，是为了让并发跑的门槛不抢同一个 ref 锁；`record-lib.mjs` 也是这么做的。整次运行固定读这个提交（`git cat-file blob <提交>:tests/interact/<id>.json`），基线 hash 比对、还原版回放的步骤、离线重算基线（`refreshBaseline` → `baseline.mjs --interact-ref <提交>`）三处读的是同一份脚本。fetch 重试 3 次，仍失败就报门槛自身错误（`{error}`）。不会悄悄退回读工作区，否则又会变成误报。用到的提交号写在结果的 `interactRef` 里。
- **page 模式**：默认仍然读本检出的工作区，行为和改前一样。
- `--interact-ref <提交>` 可以指定别的提交（会先校验提交存在）；`--interact-ref worktree` 回到读工作区。
- 页面在该提交里没有脚本时，退回 POC 脚本，再没有就是 `null`，和读工作区时的优先级一样。

**为什么选这个，不选把 `tests/interact` 合进 main 和 fast-lane**：脚本的唯一写入点是 `commitToIntegration`，每次录制、重录都只推 integration。合进 main 只能修好当下这一次，以后每录一页都要再同步一次。少同步一次，误报就会回来，而且「同步」本身还得另建机制、另走复核。直接读写入点，就没有第二份副本需要保持一致。

### 3. 为什么不算放宽

比对什么、怎么比、阈值多少都没变。改动只决定门槛从哪里取「录基线时用的那份脚本」：取的是基线录制时的同一来源，hash 仍然逐字节比较。脚本真改过的页照样报 `interaction script changed`（见用例 `a script that really changed is still reported`）。修好以后，原来被误报挡掉的页反而要真正跑完交互、做完整比对，检查只会更严。
