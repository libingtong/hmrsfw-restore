## HM-1310：快速通道合并 integration 之后，check-imports 规则 4 又把别页修正算到每一页

- 分支：`rule/hm-1310-shared-branch-merges`（基于 `main` `d8059c2`），一个提交：`rule(check-imports)`：共享分支上，区间里的合并提交不再让按提交归属整体失效，合并只算它自己改的文件。
- 提出：裁定员；复核：两个非 Anthropic 家族的复核员。
- 来源：HM-1129 督办 10-24 05:45 对 6 张快速通道单 `--regate`，其中 5 张（HM-264 `page.portal.sjz.unitMain.unitMain`、HM-335 `page.portal.sjz.bigData.components.Dashboard2`、HM-1136 `page.uc.collage.studentApply`、HM-1141 `page.uc.changeRole`、HM-1142 `page.uc.experthome`）的门槛只报了同一条 `static:imports`：「本单不能修改 `apps/portal/src/views/answer/passwordModal.vue`」。HM-1141 因此被挂起，派生了公共库升级单 HM-1309。

### 根因

HM-526 把共享分支上的规则 4 改成按提交归属判定（`otherPagesOnly`），但留了一条退路：`merge-base..HEAD` 里只要有合并提交，就整体退回旧判法（每个改动都算本单的）。理由是合并提交自己带进来的改动不在逐个提交的文件列表里。

HM-1068 之后，快速通道改为把 integration **合并**进 `restore/fast-lane`（之前是 cherry-pick，HM-990）。于是这条退路每次都会触发。hmrsfw-vue `restore/fast-lane` `0d843f8` 上的情况：

| 提交 | 说明 | 自己改的文件（`git log -c --name-only`） |
| --- | --- | --- |
| `0ee1427` | merge-base，integration 的提交，也是 `7958d12` 的第二个父提交 | |
| `434c7d2`、`47b4f8f`、`7958d12` | `Merge integration into restore/fast-lane`（HM-1068） | 无（每个文件都和某个父提交一致） |
| `0d843f8` | HM-355 修正第 1 轮 | `apps/portal/src/views/answer/passwordModal.vue`（`page.portal.answer.passwordModal` 的 `target`） |

`git diff 0ee1427...0d843f8` 只有 `passwordModal.vue` 一个文件。改它的只有 `0d843f8`，这个提交只碰了别页自己的文件，提交信息也没提这 5 页。按 HM-526 的判据，这个文件应该算 `page.portal.answer.passwordModal` 的改动。但区间里有 3 个合并提交，`otherPagesOnly` 第 127 行直接返回空表，所以它算到了每一页头上。

### 改动

`tools/check-imports.mjs` 的 `otherPagesOnly`：

- 去掉「有合并就返回空表」这条退路。
- 逐个提交列文件时加 `-c`（combined diff）：非合并提交照旧列出它改的文件；合并提交只列出**和每个父提交都不同**的文件，也就是合并自己改的部分（解决冲突、手工编辑）。合并原样取自某一侧的内容不列，因为那一侧的提交在区间里会逐个列出（或者那一侧本来就在 base 里）。
- 合并提交**一律不算别页的提交**：一个文件只要被某个合并自己改过，就照旧算本单的改动。

其他条件和 HM-526 一样：文件不属于本单、不在工作区、属于另一个页面；区间里至少有一个提交改过它；每个改过它的提交都只碰别页的文件，而且提交信息没提本单或本页。

**为什么不算放宽**：

- 判据没有变，仍然是「本单只改了自己的文件」，「本单改动」仍按 HM-526 的提交归属来算。HM-526 退回旧判法，是因为当时看不到合并自己带进来的改动。`-c` 把这部分列出来，并且一律算本单的，所以这个理由不存在了。这是同一判据更完整的写法。
- 每处改动仍然有归属：区间里的每个改动，要么来自逐个列出的非合并提交（按 HM-526 归属），要么是某个合并自己改的（算每一页的，比 HM-526 退路的范围小，但同样严格），要么在区间里找不到提交（`by.length` 为 0，照旧算本单的）。
- 合并从别的分支带进来一个提交，如果这个提交碰了本单文件或提了本单 id，照旧算本单越界（测试里有反例）。
- 不设 `HMRSFW_SHARED_BRANCH` 时不走这段代码：普通还原单、共享组件单、集成门槛、全量回归都不受影响。
- `pickedFromBase`（HM-990）没有改：有合并时它仍然什么都不排除。

**为什么不用其他做法**：

- 只看本页 `target`、`subComponentDir` 下的文件（督办单提的方向）：会放过「本单的修正员另起一个提交去改别页」的越界，HM-526 第 1 节已经说明为什么不这么做。
- 只看 `--first-parent` 或 `--no-merges`：合并自己改的文件就看不到了，解决冲突时顺手改的别页文件会被放过。新增测试里的「合并时手工编辑」反例，用 `--no-merges` 就会错。
- 等 HM-355 合进 integration 后再重跑：只能解决这一次。快速通道下一次有页面修正时，所有页又会误判。

### 回退

一个提交，`git revert` 即可。回退后，快速通道只要有合并 integration 之后的页面修正，就回到每页都误判的状态。
