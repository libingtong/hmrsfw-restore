## HM-239：还原根节点没有 class 时，原版侧取错了根节点

- 分支：`rule/hm-239-classless-root`（基于 `main` `55b43cb`），一条规则一个提交：`fix(compare): classless-root`，改 `tools/gate/compare.mjs` 的 `pickCandidate` 和 `compareRuns`，测试在 `tools/test/compare-root-pick.test.mjs`。
- 合入 `main` 后，同一个提交 cherry-pick 到工具仓库 `restore/fast-lane`。快速通道的门槛用的是那条分支上的工具，两条分支的 `tools/gate/compare.mjs` 相同，不会冲突。
- 提出：裁定员；复核：两个非 Anthropic 家族的复核员。
- 来源：HM-239（`page.portal.talents.eMap.index`，快速通道）。两轮修正都没有改代码，门槛每次都报 load、final 的 html、text 和 load 的 pixel 不一致，提示为 `HTML differs under (root) (offset 5; lengths 826/…)`、`size 1920x90 vs 1920x900`。
- 不动的东西：`rules/compare/`、像素阈值、请求集合和请求序列的判据、`SITES.*.origSel`、HAR、公共库清单、基线。

### 现象

门户的原版根选择器是 `main > *`（`tools/gate/common.mjs`）。`/talents/eMap` 在 homeView 布局下，`main` 下面有三个子元素，所以基线记了三个候选（`$RESTORE_STATE/baseline/page.portal.talents.eMap.index/baseline.json`，两次运行一样）：

| 序号 | `class` | 内容 | 截图 |
| --- | --- | --- | --- |
| 0 | `headerBox` | 布局头部，文本 13 字符 | `shot.png`，1920×90 |
| 1 | 无 | 页面根，带本页 scopeId `data-v-a9fc01f6`（与 `queue/page.portal.talents.eMap.index.json` 的 `scopeIds` 一致），文本 147 字符 | `shot.1.png`，1920×900 |
| 2 | `footCls flex` | 布局底部 | `shot.2.png` |

还原页的根是 `<div data-v-…>`，没有 `class` 属性（`apps/portal/src/views/talents/eMap/index.vue`，原 chunk `legacy-dist/portal/assets/index.178332063620096.js` 里也是没有 class 的 `div`）。`pickCandidate` 原来写的是 `cls != null && c.cls === cls`：还原根的 `class` 为 `null` 时一条也不匹配，于是退回第 0 个候选，也就是布局头部。门槛拿页面和头部比，html、text、pixel 当然全错，这和页面写得对不对无关。门槛报告 `$RESTORE_STATE/gate/page.portal.talents.eMap.index-a1/…/report.json` 里 `orig[*].cls` 两次都是 `headerBox`。

### 原版出处

homeView 布局在 `legacy-dist/portal/assets/homeView.1783320636200.js`：

| 偏移 | 内容 |
| --- | --- |
| 814 | 头部组件的根 `{key:0,class:"headerBox"}` |
| 6160 | 底部组件的根 `{class:"footCls flex"}` |
| 8412–8440 | 布局的渲染函数：`h(C,null,[i.headersName?…(动态头部组件)…, je(x) /* RouterView */, i.footName?…(动态底部组件)…],64)`，是一个 Fragment |

页面组件挂在 RouterView 的位置上，排在头部后面。头部有 class，页面根可以没有 class，"第一个候选"不一定是页面。

### 规则

`pickCandidate(cands, cls)` 区分两种情况：

- `cls` 为 `null`：还原根确实没有 class 属性。只和同样没有 class 属性的原版候选匹配，取第一个。
- `cls` 为 `undefined`：没有可匹配的还原根，比如还原侧自己的投影，或者还原页是空的。这时和原来一样取第一个候选。

`compareRuns` 相应地改：还原根存在且不为空时，把它的 `class`（可能是 `null`）传给原版侧；还原页为空时传 `undefined`。还原侧自己的投影传 `undefined`，仍取 `#poc-main > *` 的第一个元素。

其余一律不动：

- 还原根有 class 时，仍按 class 相同匹配，找不到就取第一个，和原来一样。
- 原版里没有无 class 的候选时，仍取第一个（测试第一项）。
- 选中候选以后的比较完全照旧：html、text、overlay、请求、像素都用原来的规范化和阈值。没有 class 的还原根内容不同，照样失败（测试第三项）。还原页为空，照样报 `render`（测试第五项）。
- `unstableKeys`（基线两次运行是否一致）不改。它按第一次运行第 0 个候选的 class 选，两次运行的候选顺序相同，所以结果不变。

### 为什么不算放宽

这条改的是"拿原版哪一个元素来比"，不是"比的时候放过什么"。

- 原来的写法在这种情况下必然失败：没有 class 的还原根和带 `class="headerBox"` 的头部，规范化 HTML 从根标签开始就不同（报告里的 `offset 5`）。所以现在已经通过的页面，不可能是靠这条退回逻辑通过的，这次改动不会让任何一页从通过变成失败。
- 新匹配到的候选是页面组件自己的根：它挂在 RouterView 的位置上，带本页 scopeId。这本来就是 `origSel` 注释里说的"页面组件的根元素"。
- 判据和阈值一个都没动。改完以后，还原页必须和真正的页面根逐项相同，比原来更严格：原来比的是头部，永远过不了，也查不出页面的问题。

### 影响面

在 198 份基线里，第 0 个候选有 class、同时又有无 class 候选的共 29 份（门户 28 份，用户中心 `page.uc.zcyzCorpAttestationapprove` 1 份）。只有当还原根也没有 class 时，结果才会变，而这种组合在原来的写法下一定失败。合入后会按流程对所有已通过的页面跑一次全量回归。

### 本单不处理的

`/talents/eMap` 的首个列表请求要等百度在线 IP 定位（原 chunk `index.178332063620096.js` 里的 `new t.LocalCity` → `s.get(n)`）。门槛的 `routeApi` 不拦截 `api.map.baidu.com`，HAR 里也没有百度的请求，所以定位有没有返回、地图底图和版权行能不能加载，每次运行都可能不同。HM-239 第 1 轮和第 3 轮门槛定位没有返回，第 2 轮返回了。这是外网带来的不确定，不是等价写法的问题。HAR 里没有可以作为依据的应答，本单不给它造桩，也不放宽请求判据。
