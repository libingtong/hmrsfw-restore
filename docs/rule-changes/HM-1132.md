## HM-1132：快速通道退场后，page 模式门槛误报「交互脚本已变」，录制与门槛死循环

- 分支：`rule/hm-1132-page-interact-ref`（基于 `main` `0d6a355`），提交：
  1. `rule(gate)`：`tools/gate.mjs` 的 `interactRef` 在所有模式下默认读工具仓库现取的 `origin/integration`，去掉不再使用的 `mode` 参数；用例 `tools/test/gate-interact-ref.test.mjs`；`docs/gate.md`；
  2. 本文。
- 提出：裁定员；复核：两个非 Anthropic 家族的复核员。
- 是 HM-914 的延续：同一个根因，HM-914 只修了集成模式，当时 page 模式的门槛从 `restore/fast-lane` 跑，门槛员多次手动把 integration 的 `tests/interact` 拷进检出目录（HM-290、HM-399 的工作区里有 256 个未跟踪的脚本），所以没暴露。
- 不动的东西：比对和归一化规则（`rules/compare/`）、像素阈值、请求判据、基线、HAR、公共库清单、`queue/`。

### 1. 现象

HM-1068 让快速通道退场后，快速通道任务的 `[RETIRE]` 评论要求工具仓库改用 `main`。此后 page 模式的门槛全部从 `main` 跑，而 `main` 上的 `tests/interact` 只有 8 份 POC 脚本（c02…c19）。每张录过交互脚本的页面都得到：

```
{"pending":"record","missing":[{"wo":"page.uc.zcyzJobFairRelease","why":"interaction script changed since the baseline"}]}
```

`advance` 把任务记为等录制；录制员重录，`record-page.mjs` 仍只把脚本提交到 `integration`（`commitToIntegration`），基线里的 hash 仍是 integration 那份；门槛再从 `main` 读，又是 `null`。以 HM-474（`page.uc.zcyzJobFairRelease`）为例：2026-10-22 13:53 退回录制，16:59、17:28 两次「录制已完成，重新送门槛」，17:20、17:44 两次同样的 PENDING。

核对：`$RESTORE_STATE/baseline/page.uc.zcyzJobFairRelease/baseline.json` 的 `script` 是 `73a97551…ca40`，与 `origin/integration:tests/interact/page.uc.zcyzJobFairRelease.json`（提交 `94e08b2`）JSON 规范化后的 SHA-256 逐字相同；`main` 上没有这份文件，POC 脚本里也没有，读成 `null`。

### 2. 改动

- `interactRef(argv)`：不写 `--interact-ref` 时，page、integration、upgrade 模式都 fetch 工具仓库的 `integration` 到私有 ref，固定在一个提交上读脚本，做法与 HM-914 的集成模式完全相同（重试 3 次，失败是门槛自身错误，不悄悄退回工作区）。
- `--interact-ref worktree` 仍读本检出的工作区，`--interact-ref <提交>` 仍可指定提交。
- 提交里没有该页脚本时退回 POC 脚本，再没有就是 `null`，优先级不变。

**为什么不选「门槛员改用 integration 分支的工具」或「手动拷脚本」**：前者会让门槛员跑 integration 上未经复核的工具代码；后者每张单都要做，漏一次就回到死循环。脚本的唯一写入点是 `commitToIntegration`，直接读写入点，没有第二份副本。

### 3. 为什么不算放宽

比对什么、怎么比、阈值多少都没变，只决定门槛从哪里取「录基线时用的那份脚本」。脚本真变了的页照样报 `interaction script changed`（见下表 3 页，以及用例 `a script that really changed is still reported`）。修好以后，这些页要真正执行交互步骤、做完整比对，检查只会更严：原来读成 `null` 时，还原版回放根本不执行交互。
