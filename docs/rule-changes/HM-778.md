### 1. 差异只来自构建方式，不是还原有错

原包是 `vite build` 的产物：小于 `build.assetsInlineLimit`（4096 字节）的图片内联成 `data:image/png;base64,…`。还原侧抽出来的图片文件与原 chunk 里的 data URI **逐字节相同**（解码后比对 base64，`hmrsfw-vue` `restore/fast-lane` `1b20769`）：

| 还原侧文件 | 字节 | 原 chunk 位置 |
| --- | --- | --- |
| `apps/portal/src/views/cityHome/index/assets/index-8f9ca5c3c3.png`（模板 src） | 272 | `legacy-dist/portal/assets/index.178332063620024.js:1` 偏移 2019 |
| `…/cityHome/index/assets/index-dd77ce42e2.png`（模板 src） | 512 | 同上，偏移 2432 |
| `…/cityHome/index/assets/index-a12c81a8f4.png`（模板 src） | 347 | 同上，偏移 3143 |
| `apps/portal/src/shared/auth/assets/auth-2ec256b5c2.png`（`new URL`，导出 `_`） | 493 | `legacy-dist/portal/assets/auth.1783320636200.js:1` 偏移 577 |
| `…/shared/auth/assets/auth-f02a36ee85.png`（`new URL`，导出 `a`） | 445 | 同上，偏移 4634 |
| `apps/portal/src/shared/FriendLinks/assets/FriendLinks-c91c543c6e.png`（`new URL`） | 3110 | `legacy-dist/portal/assets/FriendLinks.vue_vue_type_style_index_0_lang.1783320636200.js:1` 偏移 1075 |
| `…/FriendLinks-48323b1509.png` | 1795 | 同上，偏移 5250 |
| `…/FriendLinks-12c87f382f.png` | 2530 | 同上，偏移 7673 |

两种写法在 `vite build` 下都会内联成同一个 data URI，和原包一致；只有门槛的按需编译（vite serve）给出开发 URL：

- **模板相对 src**：`@vitejs/plugin-vue` 4.3.4 `resolveTemplateCompilerOptions` 在有开发服务器时给模板编译器 `transformAssetUrls: { base: <dev base>/<.vue 所在目录> }`，`./a.png` 被直接改写成字符串 `/src/…/a.png`，不产生 import，`buildAssetsPlugin` 的 `load` 钩子拿不到。构建时给的是 `{ includeAbsolute: true }`，相对、绝对、别名路径都转成 import。
- **`new URL(…, import.meta.url)`**：Vite 4.4.9 `vite:asset-import-meta-url` 在 serve 下用 `fileToDevUrl`（`/src/…/a.png`），build 下用 `fileToBuiltUrl`（data URI 或 `/assets/<name>-<hash>.<ext>`）。`buildAssetsPlugin` 原来只模拟 import、`?url`，不处理这种写法。

用真实的 `startOnDemand`（门槛 page 模式的同一入口）编译这三个文件，取编译结果里的资源 URL（模板 import 经服务器解析到底，`new URL` 取字面量）：

| 文件 | `main` `55b43cb` | 本分支 |
| --- | --- | --- |
| `views/cityHome/index.vue` | 3 个开发字符串 `/src/views/cityHome/index/assets/…png`，≠ 原包 | 3 个 data URI，= 原包 |
| `shared/auth.ts` | `new URL("/src/shared/auth/assets/…png")` ×2，≠ 原包 | data URI ×2，= 原包 |
| `shared/FriendLinks.vue` | `new URL("/src/shared/FriendLinks/assets/…png")` ×3，≠ 原包 | data URI ×3，= 原包 |

### 2. 改动

**`template-relative-src`**：`buildAssetsPlugin` 的 `configResolved` 找到 `vite:vue` 插件，通过它公开的 `api.options` 把 `template.transformAssetUrls` 设成构建时的值（`vueBuildAssetUrls()`：`{ base: null, includeAbsolute: true, …用户自己的设置 }`，与 plugin-vue 构建分支的结果相同）。plugin-vue 在开发服务器分支里合并 `{ base: <dev>, ...用户设置 }`，用户设置里的 `base: null` 盖掉开发 base。于是模板编译成和构建相同的 import，资源走既有的 `load` 钩子，得到和构建相同的 URL。

**`import-meta-url`**：`buildAssetsPlugin` 改为返回两个插件（Vite 会展开数组）：原来的 `gate-build-assets`（pre），加上普通顺序的 `gate-build-assets-url`。后者排在 plugin-vue 之后（SFC 已编译成 JS）、Vite 自己的 `vite:asset-import-meta-url` 之前，按构建的做法把表达式改写成 `new URL("<构建 URL>", self.location)`：

- 匹配用 Vite 4.4.9 的同一个正则（第一个参数是字符串字面量）；带 `${}` 的模板字符串是 glob，交给 Vite；
- 相对路径按导入方目录解析，其余用解析器（别名）；
- 构建 URL 用 `load` 钩子同一个 `builtUrl()`（同一个 `assetsInlineLimit`、同一张 mime 表、同样的 `.svg`/`.html`/Git LFS 例外、同样的 `assetFileNames` 和哈希），开发服务器按这个 URL 返回源文件；
- `public/` 里的文件、不存在的文件交给 Vite：这两种 serve 和 build 结果本来相同。

没有照做的一处：Vite 用 strip-literal 跳过注释和字符串里的匹配，门槛不跳过。注释里的表达式改了也不执行；字符串里写这种表达式的情况在应用里没有。

### 3. 为什么不算放宽

- 判据一个没动：DOM 比对、像素比例、请求序列、归一化规则、已知差异、公共库清单都不变。没有新增任何「忽略 src」「data URI 与 URL 视为相等」之类的规范化。
- 变的是门槛还原侧的**构建产物**：page 模式按需编译本来就承诺与 `vite build` 一致（`docs/gate.md`「资源与 `vite build` 一致」，`--build full` 一致性检查），这两种写法是该承诺的漏洞。改后按需编译的结果与真实 `vite build` 逐字相同（测试直接对比真实构建），也与原包相同（第 1 节）。
- 方向是收紧而不是放松：原来门槛里这些资源是开发 URL，与整站构建、与原包都不同；改后与两者都相同。如果还原侧图片内容错了，data URI 照样不同，像素照样不同，照样失败。
- 整站构建路径（integration、`--regress`、`rule-regression`）不经过这个插件，回归结论不会因为本变更变化；变化只在 page 模式，并且是向整站构建靠拢。

### 4. 既有用例的断言修正（第 1 个提交）

`gate-assets.test.mjs` 原有用例最后断言「发出的资源恰好 2 个」，前提是「应用自身的图片都小于内联上限」。现在 `hmrsfw-vue` 有 3 张超过上限的图片，这条断言在 `main` 上就失败（URL 逐个比对全部一致）。改为检查三个合成文件都按预期出现（`big+name` → `/assets/big_name-…`、刚好 4096 字节的 `edge` 发出、4095 字节的 gif 内联）。只改断言，不改 URL 比对。

### 5. #1 的二选一：选门槛侧修复

HM-429 提了另一种解法：把共享层 `apps/portal/src/shared/auth.ts` 改成 `import` 写法，走公共库升级单。裁定选门槛侧修复，理由：

1. **根因在门槛**。`new URL("./a.png", import.meta.url)` 是 Vite 官方支持的写法，`vite build` 结果与原包一致（第 1 节）；不一致只发生在门槛的按需编译。改共享层是让还原代码去迁就门槛的缺陷。
2. **改共享层只修一处**。同样写法在 `restore/fast-lane` 上有 13 个文件：共享层 `shared/auth.ts`、`shared/FriendLinks.vue`、uc `shared/images.ts`，页面文件 `views/jobMarket/index.vue`、`views/login/IdentityModal.vue`、`views/xjhm/bigData/statistics.vue`、`views/talents/…`、uc `views/myPoints.vue` 等。走升级单只能修 `auth.ts`，其余页面以后还会一个个踩到（HM-240 已经为此把 `customerService/index.vue` 改回 import）。模板相对 src（#2）根本没有页面侧解法。
3. **升级单本身有风险**。HM-429 的回执指出：`tools/registry.mjs` 重新生成 component 类 chunk（auth）会丢掉 `_`、`a` 的 aliases，已还原的 guide 两页届时 `check-imports` 会判旧名。

所以 HM-429（#1）改为不需要，由裁定员关单；HM-430（#2）的回执本来就是「升级单不适用」，一并关闭。
