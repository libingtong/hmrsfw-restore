### 1. 问题：两边比的不是同一个元素

门槛按选择器取「页面根」的候选：原版是 `SITES.portal.origSel = "main > *"`，还原版是 `REST_SEL = "#poc-main > *"`（`tools/gate/common.mjs`）。

**原版侧的 `main > *` 包含布局的头部和底部。** 门户的布局 homeView 渲染的是一个 Fragment，里面依次是头部组件、`RouterView`、底部组件：

| 文件:偏移 | 内容 |
| --- | --- |
| `legacy-dist/portal/assets/homeView.1783320636200.js:8416` | `h(C,null,[i.headersName?(…O(ne(i.headersName),…)):L("",!0),je(x),i.footName?(…):L("",!0)],64)`：Fragment[头部, RouterView, 底部] |
| `legacy-dist/portal/assets/homeView.1783320636200.js:821` | 头部根 `{key:0,class:"headerBox"}` |

所以原版基线的候选依次是 `headerBox`、页面自己的根（页面是多根组件时有好几个）、`footCls flex`（`$RESTORE_STATE/baseline/<id>/baseline.json`）。还原版在 page 模式下页面直接挂成顶层路由，`#poc-main` 下没有 homeView，`candidates[0]` 就是页面根。

**改动前怎么选。** `compareRuns` 取还原版 load 阶段第一个候选的 class（`restRoot`），load 和 final **两个阶段**都拿它去原版候选里找同 class 的那个；`pickCandidate` 找不到时，或者 class 是 `null` 时（`cls != null &&`），静默回落到 `candidates[0]`，在门户上就是布局头部 `headerBox`。

**webFair.detail（HM-241）。** 页面根是 v-if / v-else 两个分支，滚动后换分支：

| 文件:偏移 | 内容 |
| --- | --- |
| `legacy-dist/portal/assets/detail.178332063620012.js:1841` | `Y={key:0,class:"bgBoxTop xf-relative"}` |
| `legacy-dist/portal/assets/detail.178332063620012.js:2134` | `L={key:1,class:"bgBoxTop xf-relative noTopShow"}` |
| `legacy-dist/portal/assets/detail.178332063620012.js:7115` | 滚动回调 `ee()`：`document.documentElement.scrollTop>200&&e.topShow?e.topShow=!1:…` |

交互后页面向下滚动，两边的根都变成 `bgBoxTop xf-relative noTopShow`。原版 final 候选里没有 `bgBoxTop xf-relative`，于是回落到 `headerBox`；还原版 final 取的是自己的页面根。门槛报告 `$RESTORE_STATE/gate/page.portal.talents.fair.webFair.detail-a1/…/report.json` 的失败项只有 `final.html`（根下 826/395 字符）和 `final.text`（13/0 字符）：826 字符、13 个字的正是布局头部。

**eMap.index（HM-239）。** 页面根 `div > div.jyEmap` 外层的 `div` 没有 class，`restRoot` 是 `null`，load 和 final 都回落到 `headerBox`。回执里「原版截图高 90px」就是头部的高度。

**用原数据核对。** 用两次原版运行里 class 等于还原版 final 根的候选（`bgBoxTop xf-relative noTopShow`），按当前规则规范化，`final.html`、`final.text` 与报告里存的还原版投影逐字相同。也就是说，这一页的 final 阶段本来就和原版一致，失败完全来自选错了元素，不是还原有差异。

### 2. 改动

- `pickCandidate(cands, cls)`：`cls` 为 `undefined` 时取第一个候选，用于还原侧，`#poc-main` 下只有页面；否则只取 class 属性**等于** `cls` 的候选，`null` 表示没有 class 属性。找不到时返回 `null`，不再回落到 `candidates[0]`。
- `project(run, { cls: { load, final } })`：两个阶段分别用还原版**该阶段**根的 class 去找原版候选，load 用 load 的根，final 用 final 的根。找不到时，这一阶段的 html、text 投影为 `null`，并记 `root[阶段] = false`。
- `compareRuns`：
  - 所有原版运行在某一阶段都找不到对应的根时，报失败项 `{check: "root", where: "load"|"final"}`，提示里列出还原版根的 class 和原版候选的 class，只有元素 class，没有页面文本。这一阶段的 html、text 不再拿另一个元素去比。
  - 只有部分原版运行找到根时，只和找到的那几次比。没找到的那次不参与比较，也不参与通配掩码（volatile mask）。
  - 其余逻辑不变：overlay、requests、steps、像素比对、已知差异。
- `unstableKeys`（录制时判断原版是否稳定）：final 阶段改用 run A 的 final 第一个候选的 class，原来用的是 load 阶段的。门户上这两个都是 `headerBox`，结果不变，见第 4 节。

### 3. 为什么不算放宽

- **比的内容不变，只是对齐比对对象。** 规范化规则、阈值、判据都没动。改动前，同一个页面根在 load 阶段比的是页面根，在 final 阶段比的可能是布局头部，两边比的不是同一层，比较本身没有意义。改动后，两边比的都是「该阶段的页面根」。
- **不会因为找不到就放过。** 找不到对应的根时，原来静默改比 `headerBox`，结果几乎必然失败，但提示是误导性的 html 差异；现在明确报 `root` 失败，同样不通过。用例第 3 项覆盖这种情况。
- **比原来严的一处。** 只有一次原版运行找到根时，原来另一次会拿 `headerBox` 参与通配掩码：`headerBox` 和页面根之间几乎处处不同，掩码会变成接近「什么都匹配」。现在没找到根的那次不参与掩码，还原版必须和找到的那次逐字相同（用例第 4 项）。
- **class 仍然参与比较。** 匹配只用来决定比哪个元素。class 属性本身仍在 html 里逐字比较，所以还原版根的 class 写错时，要么找不到对应的根（报 `root`），要么找到的是同 class 的元素、内容照常比。
- **没有改布局语义。** 没有让原版侧跳过布局头部，也没有改 `origSel`。这些都会改变录制和基线，本单都不做。

### 4. 验证

- **全部原版基线**：`$RESTORE_STATE/baseline/` 下有两次运行的 198 份基线，用 `main` `55b43cb` 和本分支的 `compare.mjs` 分别重算 `unstableKeys`，脚本只读基线。两边结果逐项相同，都是 9 页不稳定，没有任何一页的结果改变。
- **已有门槛报告**：`$RESTORE_STATE/gate/` 下有对应基线的报告共 16 份。分别用改动前、后的选根方式，对每份报告重新取原版投影，与报告里存的还原版投影比较。只有 2 份的比对对象变了：
  | 页面 | 改动前与还原版相同的项 | 改动后与还原版相同的项 |
  | --- | --- | --- |
  | `talents.fair.webFair.detail`（HM-241） | `load.html`、`load.text` | `load.html`、`load.text`、`final.html`、`final.text` |
  | `talents.eMap.index`（HM-239） | 无 | `load.text`、`final.text` |

  eMap 的 html 仍然不同，原因是百度地图在线定位：门槛不从 HAR 应答 `api.map.baidu.com`，还原侧地图停在 0,0。这与选根无关，本单不处理，见第 5 节。其余 14 份报告的比对对象和结果都不变。
- **测试**：新增 `tools/test/compare-root-pick.test.mjs`，5 项，用的是和 webFair、eMap 同样的结构（布局头部、页面根、布局底部；还原侧只有页面根）：
  1. 交互后根的 class 改变：final 比的是原版的 final 根；final 根内容不同、load 根内容不同时，照样失败；
  2. 还原版根没有 class：匹配原版没有 class 的候选，不匹配布局头部；内容不同时照样失败；
  3. 找不到同 class 的候选：报 `root`，不改比别的元素；
  4. 只有一次原版运行找到根：只和那一次比，不用掩码放过；
  5. `unstableKeys` 照常区分稳定和不稳定。

  前 4 项在改动前的 `compare.mjs` 上全部失败，在本分支上全部通过。
- **全量回归**：合入后由 `mergeRule` 开 `rule-regression` 跑。按上面的分析，只有比对对象被纠正的页面结果会变；原来比对对象就对的页面，选到的元素不变，结果逐字相同。

### 5. 本单不处理、另行跟进

- eMap.index 的百度地图在线定位：门槛 `routeApi` 不拦截 `api.map.baidu.com`，load 阶段的列表请求和交互超时取决于外网。要做的是给定位一个确定的应答，属于门槛回放流程，不是比对器问题。
- 多根页面只比第一个根：还原侧的 `candidates[0]` 只是多根页面的第一个根，例如 webFair.detail 的 `bgBoxTop`，后面的 `main padB30 fairDetail` 等不参与 html、text 比较。这是另一处比较范围的问题：要扩大比较范围，就会改变判据，应另开单评估。本单不扩大也不缩小比较范围。
- `unstableKeys` 在门户上只看第一个候选：录制时判断原版稳不稳定，只看了 `headerBox`。门槛比对的通配掩码直接从两次运行的页面根算，不受影响。这件事只影响 `record-page` 的 `unstable`，也另行评估。
