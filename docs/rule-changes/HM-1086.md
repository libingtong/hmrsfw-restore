## HM-1086：全量回归单的 `workOrders` 一项就超过元数据 8 KB 上限，tick 建单失败

- 分支：`rule/hm-1086-meta-pack`（基于 `main` `1a676d7`），提交：
  1. `fix(tick)`：`tools/lib/multica.mjs` 新增 `encodeMeta` / `PACK_PREFIX` / `PACK_MIN`，`setMeta` 写对象时用它；`decodeMeta` 解 `z1:`。`tools/lib/pipeline.mjs` `resumeCreations` 改为逐单 `safe`。`tools/lib/fake-multica.mjs` 按 HM-876 的式子拒绝超限写入。`tools/test/fixture.mjs` 的 `meta()` 改用 `decodeAll`。新增用例 `tools/test/scheduler.test.mjs`「HM-1086」。另改 `docs/scheduler.md`、`docs/gate.md`；
  2. 本文。
- 提出：裁定员；复核：两个非 Anthropic 家族的复核员。
- 来源：调度 tick（2026-10-22T07:44Z）报 `multica issue metadata set failed (exit 5): Invalid request: metadata exceeds the 8KB size limit`，`issue=null`。
- 不动的东西：比对、归一化规则（`rules/compare/`）、像素阈值、请求判据、门槛结论、基线、HAR、公共库清单、`gate.mjs`。回归跑哪些页（`passedPages`）不变，只改元数据**怎么存**。

### 1. 根因

把工作区全部 1101 张单的元数据按 HM-876 的式子（Σ(键名 + 存储值 + 8) + 8）算了一遍，只有一张超限：

| 单 | 状态 | 元数据 | 说明 |
| --- | --- | --- | --- |
| HM-1072 `[integration] rule-regression (254 页)` | backlog、未指派 | 只有 `kind`、`purpose`、`workOrders`，共 **8188** 字节 | HM-1060 规则合并（`1a676d7`）后 `mergeRule` → `openIntegration` 建的全量回归单 |

`finishCreate` 按 `kind`、`purpose`、`workOrders`、`sha`… 的顺序逐键写入。`workOrders` 是 254 个页 id 的 JSON，存储后 8109 字节。写到第四个键 `sha`（空串）时总量变成 8188 + 3 + 0 + 8 = 8199，超过 8192，被平台拒绝。这次失败抛在 `processRuleReviews` 的 `safe(null, …)` 里，所以 anomaly 没带单号。账本里这张单 `assigned: false`，之后每轮 `resumeCreations` 都会重试并再失败。`resumeCreations` 的循环没有逐单兜底，排在它后面的中断建单也补不完。

这是**脚本问题**，不是单据问题：已通过页面越多，`workOrders` 越长。192 页的 HM-1031 已有 7017 字节，过了 250 页左右，单这一项就放不下（集成单的 `gate.<attempt>` 本来也要在剩下的空间里写）。HM-876 只修了 `gate.<attempt>` 的预算，没有处理 `workOrders` 本身。

后果：HM-1060 规则已合入 `main`，但合并后的全量回归至今没有指派出去。

### 2. 改动

- **大值压缩**（`encodeMeta`）：对象或数组的 JSON 超过 2048 字节时，写成 `z1:` + base64(deflate-raw, level 9)，否则照旧写 JSON 文本。`decodeMeta` 遇到 `z1:` 前缀就解压后 `JSON.parse`，解不开时原样返回。调度脚本读元数据都经过 `decodeMeta` / `decodeAll`：`pipeline.mjs` 通过 `Multica` 类，`gate.mjs` 的 `taskMeta` 直接调 `decodeAll`，`route.mjs` 通过 `listIssues`。所以读取方都不用改。2 KB 以下的值（restore 单的 `workOrders`、`history`、`receipt.<n>` 等）写法和改前逐字节相同。
- **建单补完逐单兜底**（`resumeCreations`）：每张单包一层 `safe(id, …)`。某张单再失败时，anomaly 会带上它的单号，后面的单照常补完。
- **假 multica 也执行上限**：`fake-multica.mjs` 在 `metadata set` 时按 HM-876 的式子算总量，超限就返回与平台相同的 `metadata exceeds the 8KB size limit`。以后的场景用例能直接暴露这类问题。

### 3. 实测数字（用工作区真实元数据离线核算）

| 单 | 页数 | 改前总量 | 改后总量 |
| --- | --- | --- | --- |
| HM-1072 完整元数据（`openIntegration` 要写的 11 个键） | 254 | **8467 > 8192** | 2693（`workOrders` 2335） |
| HM-1031 | 192 | 7017 | 2592 |
| HM-1023 | 187 | 6888 | 2557 |
| HM-816 | 61 | 6991 | 6991（`workOrders` 2152，未超阈值不压缩；大头是门槛写的 `gate.1`） |

按同样的 id 形态外推，1000 页压缩后约 6 KB。

### 4. 为什么不算放宽

门槛的输入、比对和结论都没动，回归页集合也没动。只是同一个数组换了一种无损编码存放，读回来与原数组逐元素相等（用例断言 `deepEqual`）。

### 5. 验证

- 新用例 `HM-1086`（`node --test --test-name-pattern='HM-1086' tools/test/scheduler.test.mjs`）：130 个长 id（JSON 9.2 KB，单这一项就超限）的规则变更批准后，全量回归单建成并指派（`todo`）。`workOrders` 以 `z1:` 存储，读回与原列表相同，总量小于 4 KB。账本里还造了两张中断建单：一张大 `workOrders`（HM-1072 形态）下一轮补完；另一张怎样都超限，anomaly 带上它自己的单号，且不影响前一张。
- 对照：把 `PACK_MIN` 设为不压缩时同一用例失败（见复核单评论中的运行记录）。
- 回归：`scheduler`、`gate-report`、`gate-advance`、`fast-lane`、`machines`、`concurrency` 六个测试文件的结果见复核单评论。

### 6. 合入后

不用人工操作：下一轮 tick 的 `resumeCreations` 会重新写 HM-1072 的全部元数据。`workOrders` 改为压缩形态覆盖原值，后续键都能写进去，然后指派门槛员，跑 HM-1060 规则的全量回归。已有的未压缩单照常可读。
