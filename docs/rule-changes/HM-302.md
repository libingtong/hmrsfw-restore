## HM-302：原版自己两次运行就画得不同的 `<canvas>`，像素比对不比这块画布

- 分支：`rule/hm-302-volatile-canvas`（基于 `main` `a7a4bdc`），只有一个规则提交：`rule(compare): volatile-canvas`。规则文件是 `rules/compare/50-volatile-canvas.json`（`kind: param`，`enabled` 改成 `false` 即停用）。实现分布在以下几处：`tools/gate/replay.mjs`（`canvasBoxesInPage`，截图时记录根内画布的位置和大小）、`tools/gate/compare.mjs`（`volatileCanvases`、`pixelDiff` 的 `masks`）、`tools/gate/rules.mjs`（读参数）、`tools/baseline.mjs`（基线写入 `canvases` 和 `canvasBoxes: true`）、`tools/gate.mjs`（旧基线离线重算；`report.json` 写 `volatileCanvases`）。测试文件是 `tools/test/compare-volatile-canvas.test.mjs`。
- 合入 `main` 后，同一提交 cherry-pick 到工具仓库 `restore/fast-lane`（分支 `rule/hm-302-fast-lane`），做法与 HM-273、HM-652 相同。
- 提出：裁定员。复核：两个非 Anthropic 家族的复核员。
- 以下内容不变：像素阈值 `maxRatio` 0.5% 和 `threshold` 0.1，HTML、文本、请求集合和请求序列的判据，HAR，公共库清单。

### 1. 现象

`page.portal.talents.setUp.setupList`（HM-302，快速通道）的公共库升级（HM-819，补上 TagCanvas 库）合入后，门槛 a2 跑了三次，失败项只剩加载阶段的像素差：0.919%、0.936%、0.994%。HTML、文本和请求都已通过。差异目录是 `$RESTORE_STATE/gate/page.portal.talents.setUp.setupList-a2`，还原版 commit 是 `bf4d726`。

用基线截图和门槛截图逐对重算（pixelmatch，threshold 0.1，1920×760）：

| 对比 | 差异像素 | 差异包围盒 |
| --- | --- | --- |
| 原版 run 1 和原版 run 2（`baseline/…setupList/shot.1.png`、`shot.r2.1.png`） | 0.778% | (1285,204)–(1534,383) |
| 原版 run 1 和还原版 `rest.png` | 0.971% | 同上 |
| 原版 run 2 和还原版 `rest.png` | 0.940% | 同上 |
| 原版 run 2 和还原版 `rest.retry.png` | 0.994% | 同上 |
| 还原版两次之间（`rest.png` 和 `rest.retry.png`） | 0.737% | 同上 |

所有差异都在「热门领域」卡片里的 TagCanvas 画布内，画布外一个像素都不差。原版自己两次运行之间就差 0.778%，已经超过 0.5% 的上限。也就是说，即使把原版拿来和原版比，这一页也过不了门槛。基线的 `unstable` 是空的，原因是 `unstableKeys` 用的根候选是 `candidates[0]`，在 /talents 布局下它是页头（HM-302 第一次裁定时已指出）。改用页面根本身比较，就是上表第一行。

### 2. 原因：画布内容取决于随机数和时间

原 chunk `legacy-dist/portal/assets/tagcanvas.vue_vue_type_style_index_0_lang.1783320636200.js`（还原版 `apps/portal/src/shared/tagcanvas.vue` 与它逐项一致）：

| 内容 | 偏移 |
| --- | --- |
| 库本体 `shuffle`：`e=~~(Math.random()*i)` 打乱数组 | 889 |
| 库本体按 `shuffleTags` 打乱标签顺序 | 30876、40906 |
| 库本体用 `requestAnimationFrame` 持续重绘（球体一直在转） | 13772、28194 |
| 组件选项 `shuffleTags:!0`、`initial:[.1,.1]`、`fadeIn:800` | 42146 起 |
| 组件 `TagCanvas.Start("world-cloud-canvas","weightTags",F)` | 42453 |
| 组件给每个标签取 class：`Math.random()>.5?"huge":"large"` 或 `"medium":"small"` | 42878、42935 |
| 组件给每个标签取颜色：`x[Math.floor(Math.random()*x.length)]` | 43519 |

所以，每次运行时标签的颜色、字号、在球面上的顺序都是随机的，截图时球转到哪个角度则取决于页面多久稳定下来。这些都属于原版自身的不确定，两边代码相同，画出来的结果也不同。HTML 里 `#weightTags` 下的 `<a>`（颜色、class）走的是现有的易变掩码（`volatileMatch`），所以 HTML 已经通过。像素比对没有对应的掩码，因此只能失败。

### 3. 改动

**截图时记录画布位置**（两边都记）。`captureRoot` 每截一张根截图，就用 `canvasBoxesInPage` 记下根内可见的 `<canvas>` 在截图中的整像素外接框，写在候选的 `canvases` 字段里；`display:none`、`visibility` 不是 `visible`、面积为 0 的画布不记。

**比对时去掉易变画布**（`volatileCanvases`）。一块画布要同时满足以下几条，才从像素比对里去掉：

1. 原版两次截图和还原版截图都有这块画布，位置和大小相差不超过 1 px；
2. 三张截图尺寸相同；
3. 原版两次截图在这块画布的框内有差异（pixelmatch，阈值同上，至少一个像素）。

去掉的区域是三个框的并集，再向外扩 1 px（用于吸收整像素取整误差）。去掉的方式是：还原版在框内取原版的像素，同时这些像素也从分母里扣除，比例按「实际比较的像素」计算，不会被大面积相同区域摊薄。框外照常逐像素比较，阈值不变。

**代替逐像素比较：着墨比例**。被去掉的画布，用「与框内最常见颜色不同的像素占比」来衡量画了多少。还原版的着墨比例必须落在 [0.5 × 原版两次中较小的, 2 × 原版两次中较大的] 之内（`inkRange`），否则报 `pixel` 失败。提示里只写框的位置和几个比例，不含页面文字。下面两种情况都会被拦下：

- 画布空白（库没加载、`Start` 抛错被吞掉，即 HM-302 门槛 a1 的情况）；
- 画布画了明显不同的东西。

画布本身（`<canvas>` 元素、属性、`style` 高度）和它读取的标签列表（`#weightTags`）仍按 HTML 照常比较。

**两次原版运行**（`unstableKeys`）用同样的掩码。原版只是画布易变的页面，不再因此被记成 `load.pixel` 不稳定。

**为什么不算放宽**：

- 阈值没有动。被去掉的只是原版自己两次就不同的像素区域，这和 `compare.mjs` 对 HTML、文本已有的易变掩码是同一个原则：原版自身不稳定的位置不比较。
- 范围收得很窄：只针对 `<canvas>`（它的内容不在 DOM 里，没有别的办法比较），要求三边同位置同尺寸，且原版两次确实不同。
- 稳定的画布照常逐像素比较，例如两次画得一样的 echarts 图表；测试里断言了这种情况仍然失败。位置不对、还原版缺画布、旧基线没有画布框，都不去掉。
- 代价是：易变画布里「画在哪个位置、用什么颜色」不再逐像素比较，只比较着墨比例。这部分本来就无法比较，原版和原版比也通不过。

**为什么不让画布内容可重复**（对照 HM-273 的做法，即让回放可重复）：

- 颜色和 class 在组件里调用 `Math.random`，打乱顺序在库里调用 `Math.random`。要让两边结果相同，只能在两边给全局 `Math.random` 设同一个种子，并且要求在这之前两边调用 `Math.random` 的次数和顺序都一样。但两边的 Vue（3.2.47 和 3.3.4）、ant-design-vue（3.2.15 和 3.2.20）以及构建产物都不同，这个前提不成立。
- 球体转动由 `requestAnimationFrame` 驱动，回放时钟是真实流逝的（`page.clock.setSystemTime` 只固定起点）。要固定转动角度，就得冻结全部动画时间，影响面远大于这一块画布。

### 4. 旧基线

旧基线没有记录画布框。`baselineFor` 对没有 `canvasBoxes` 标记、且任何一次运行的加载截图根里含 `<canvas>` 的基线，返回 `refresh`：门槛用基线自己的 HAR 离线重跑 `baseline.mjs`，不访问测试环境，处理方式与 HM-253、HM-342、HM-380、HM-273 相同。重算只多记一个 `canvases` 字段，截图、DOM、请求的取法不变。

### 验证

- **本页真实截图**：用现有基线和门槛 a2 的两张还原版截图，画布框按差异包围盒外扩 10 px 近似为 (1275,194) 270×200，跑 `compareRuns`。规则停用时，结果与门槛一致（0.940%、0.994%，失败）；规则启用时，框外像素差为 0，着墨比例原版 14.8% / 11.5%、还原版 16.5% / 17.8%，在 [5.8%, 29.6%] 内，通过。门槛 a1 那种空白画布没有留下截图，这种情况由下面测试里的「画布空白」反例覆盖。
- **测试**：`node --test tools/test/compare-volatile-canvas.test.mjs`，5/5 通过：
  - 原版两次不同的画布：规则停用时失败，启用时通过，掩码等于三框并集外扩 1 px；`unstableKeys` 不再记 `load.pixel`；
  - 还原版画布空白、或画得过满：失败，提示里给出着墨比例；
  - 框外有差异：照常失败；
  - 稳定画布、位置偏 2 px、还原版没有画布、旧基线没有画布框：不去掉，照常失败；偏 1 px 视为同一块；
  - `canvasBoxesInPage`（Chromium）：元素截图和 clip 截图两种原点、小数坐标、不可见画布、根外画布。
- 工具仓库已有测试全部重跑（`node --test tools/test/*.test.mjs`），结果见 HM-302 评论。
- **本页实测**：裁定员没有 `RESTORE_ASSETS`，不能自己回放。合入并同步到 `restore/fast-lane` 后，由门槛员对 HM-302 执行 `--regate`；门槛会先离线重算本页基线。
- **全量回归**：合入后由 `mergeRule` 开 `rule-regression` 集成门槛。会变的只有两种页面：一种是原来因原版易变画布而失败的，可能由失败变通过，这正是本变更要消除的误判；另一种是还原版画布与原版着墨差距过大的，由于新增了着墨检查，可能由通过变失败，这是变严。

### 回退

`git revert` 这一个提交，或者把规则文件的 `enabled` 改成 `false`。带 `canvasBoxes` 的基线不用重算：停用后不再读 `canvases` 字段，截图本身没有变化。
