### 0. 这条规则此前已经被合入又被回退，这次是什么变了

这条规则第一次由 HM-1417/HM-1379 提出，`rule/hm-1379-static-img-not-in-har` 于 `c1984f97` 合入 main（2026-10-25 05:17 CST），随后 `ded73779`（12:06 CST）把它整条回退，理由是「`full regression failed on 274 pages`」——和同一批次的 hm-1382、hm-1432 一起被回退（HM-1471 记录了这是「有页失败就回退」policy 的连锁误伤，HM-1471 是另一张单，不在本单范围内，止血和回退判定逻辑的修复见 HM-1471）。

本单核实过这不是空穴来风：回归 run `a4e8f558f9c9ddd8`（`$RESTORE_STATE/gate/runs/a4e8f558f9c9ddd8`，`tools` 字段正是 `dffa9cd`，即 hm-1379 合入后的 main，确认这次回归确实跑在带有黑图 bug 的代码上）274 页里 75 页失败，其中 **53 页**是 `pixel` 失败（HM-1471 描述里说的「7 页」只统计了每页第一条失败项，漏掉了同一页里排在 html 差异之后的 pixel 差异）。这 53 页里，**19 页**和本单独立核算出的「DOM 引用了本基线 HAR 没有的 `/common/static/` 图片」名单精确重合（`page.uc.CorpAttestation`、`page.uc.CorpCenter`、`page.uc.main`、`page.portal.sjz.virtualjobfairs.index` 等，见第 4 节核算方法），可以确认是本次改动要修的这个 bug；其余 34 页 pixel 失败和全部 68 页 html 差异，大概率是同一批次 hm-1394（mask-match）、hm-1385（motion-state）两条归一化规则当时已被回退、掩码规则一撤销原本被等价规范化掉的差异又冒出来（HM-1471 自己的判断），不在本单范围内，已经按原文转述到 HM-1471 供参考，不在本文重复分析。

**为什么还要重新提出，而不是等 HM-1471 把回退策略修好再说**：黑色像素这个 bug 本身是确定的、字节级可验证的问题（见第 1 节），不依赖对「回退是否误伤」的判断——不管回退 hm-1379 是不是误伤，这份静态图回退的实现本身有 bug，重新提出时必须先修好这个 bug，否则就算 HM-1471 的止血逻辑判定这次回退是误伤、把它恢复回来，恢复的还是这份有 bug 的实现。两件事独立：HM-1471 管「要不要恢复/回退判定怎么改」，本单管「这份具体实现对不对」。

### 1. 根因：GIF 字节没有调色板，也没有透明扩展

`notInHarResponse`（原 HM-1417）对命中不到 HAR 的 `/jeecg-system/sys/common/static/` 图片请求回一张写死的 1×1 GIF，注释里明确写着意图是「透明」，但原实现的字节：

```
R0lGODlhAQABAAAAACwAAAAAAQABAAACAkQBADs=
```

解出来是 `47 49 46 38 39 61 01 00 01 00 00 00 00 2c 00 00 00 00 01 00 01 00 00 02 02 44 01 00 3b`：Logical Screen Descriptor 的 packed 字节是 `00`，没有全局调色板（GCT flag = 0），图像描述符也没有局部调色板，更没有 Graphic Control Extension（没有 `21 f9` 块）。没有调色板时单像素的颜色索引无处可查，Chrome（以及其它主流浏览器）对这类 GIF 的默认处理是画成黑色，而不是透明——`<img>` 确实解码成功（1×1，不再塌成 0×0，原意图达到了），但颜色不对。

`page.uc.sceneFairSign`（HM-407）的 `GuideAlert` 轮播图 `<img class="radius10" style="width:100%">`：容器给了 100% 宽度，1×1 的黑色图被拉伸铺满整个轮播区域，99.934% 的像素因此和基线不一致，「下一步」按钮被挤出视口（HM-407 门槛第 2 次，`gate.2`：`"pixel":99.934,"size":"1652x730 vs 1652x730"`）。

### 2. 改动一：真正透明的 1×1 GIF

把字节换成经典的「spacer.gif」：

```
R0lGODlhAQABAIAAAAAAAP///yH5BAEAAAAALAAAAAABAAEAAAIBRAA7
```

解出来：Logical Screen Descriptor packed = `10000000`（GCT flag = 1，2 色表：`000000`/`ffffff`），紧跟一个 Graphic Control Extension（`21 f9 04`，packed 字节第 0 位 = 1 即启用透明，透明色索引 = 0）。两个浏览器（原版和还原版的回放都用同一个 Chromium）都会把它画成「空白/透明」，而不是黑色。常量改名 `BLANK_GIF` → `TRANSPARENT_GIF`。

`--selftest` 原来只检查 `content-type`（`image/gif`），这正是第一次实现的 bug 能混进来、一路通过复核和回归（直到全量像素比对才暴露）的原因——是 GIF 没错，但没人检查这张 GIF 到底画出来是什么颜色。新增一条用例，按字节解析 GCT flag 和 GCE 的透明位：拿第一次实现的旧字节喂它会得 `false`（已用 node 脚本手工验证），拿新字节会得 `true`。

### 3. 改动二：基线失效判据——`baselineFor` 原来不知道这类基线已经过期

`tools/gate.mjs` 的 `baselineFor` 已经有一组「同一份 HAR，离线重算」的失效判据（HM-251 根选择器、HM-253/HM-342 off-scope、HM-380 零面积根截图、HM-302 canvas 盒子），但完全没有覆盖「静态图回退的渲染方式变了」这件事——`rulesAtRecord` 字段只记 `rules/compare/` 的哈希，和 `tools/gate/har.mjs` 这类门槛自身工具代码的改动完全不挂钩。这是第一次实现的一个遗漏，不只是字节的问题：即使这次字节一开始就是透明的，第一次合入之前录的基线，如果页面引用了一张 HAR 没录到二进制的 `/common/static/` 图片，录制时这张图解码失败塌成 0×0；规则生效后再跑门槛，回放会得到一个有真实几何尺寸的盒子——基线和回放的布局从一开始就对不上，和颜色对不对是两件独立的事，补字节不能自动把这个也修好。

新增一条判据，和既有几条同一个风格：

```js
if (!b.staticImageOk && b.runs.some((r) => staticImageGap(r, b.har.path)))
  return { missing: "static-image fallback changed since the baseline (HM-1417/HM-1460)", refresh: b.har.path };
```

`staticImageGap(r, harFile)`：只看 `r.load.candidates`（和 HM-380/HM-302 的判据一样只覆盖 load，不覆盖 steps/final——目前观察到的这类静态图都是首屏轮播图/封面图，不是交互后才出现的），从 candidate 的 `tree`（序列化后用正则抓 `["src","…"]`）里找 `/jeecg-system/sys/common/static/` 的 `src`，和 `loadHar(harFile)` 实际记录的请求路径集合比对；只要有一个 `src` 不在 HAR 里，就判定这个 run 受影响。`tools/baseline.mjs` 给新录的基线打上 `staticImageOk: true`，有这个标记的基线跳过这条判据。

**为什么不直接判「HAR 里有没有 `/common/static/` 请求」，要比对 DOM 里真正用到的 `src`**：避免基线完全没用到这类图片、或者图片确实被 HAR 录到了（不走回退路径）的页面被误判失效、白白重算一次。

### 4. 为什么不算放宽

- **判据不变**：两处改动都不碰 `rules/compare/` 的归一化规则、像素阈值、请求匹配判据；`staticImageGap` 只决定「这份基线要不要被当作过期重算」，重算用的还是同一份 HAR、同一套比对逻辑。
- **两侧同一处理**：`notInHarResponse` 是 `baseline.mjs`（原版）和 `gate.mjs`（还原版）共用的同一个函数，字节改动对两边一视同仁。
- **不是为了让某一页通过而改**：改动覆盖的是任意页面里任意一张走这条回退路径的图片；基线失效判据同样是通用判据，不针对某个具体工单。
- **fast-lane 工具分支检查**：`hmrsfw-restore` 的 `restore/fast-lane` 分支（`3d81c9a`，2026-10-25T05:59 CST）的 `tools/gate/har.mjs` 停留在 HM-992 之前，从未合入过 HM-1417/HM-1379，也就没有这条回退逻辑；HM-914 的结论是 fast lane 退休（HM-1068）之后页面门槛统一从 `main` 的工具代码跑（`restore/fast-lane` 只是被判的 hmrsfw-vue 应用分支）。HM-407 本身就是 fast-lane 工单，`gate.2` 确实命中了黑色图的 bug，印证门槛跑的是 `main` 的 `har.mjs`，不是 fast-lane 分支自己过时的那份——不需要也不应该把这条改动重复合到 `restore/fast-lane`。
