### 2. 机制：关闭时在 display:none 下再对齐一次

ant-design-vue 弹层的定位链是 vc-trigger `PopupInner` → vc-align `Align` → dom-align。原版包（3.2.15）和还原版依赖（3.2.20）这段逻辑相同：

| 位置 | 内容 |
| --- | --- |
| `useVisibleStatus`：原版 `legacy-dist/portal/assets/index.1783320636200.js` 偏移 232469；还原版 `ant-design-vue/es/vc-trigger/Popup/useVisibleStatus.js` | `StatusQueue = ['measure','align',null,'motion']`；`watch(visible, () => setStatus('measure'))`：**任何** visible 变化（包括关闭）都走 measure → align |
| `alignDisabled`：原版偏移 251824；还原版 `PopupInner.js:130` | 状态为 `align` / `stable` 时对齐开启，不看 visible |
| `Align` 调用：原版偏移 252534；还原版 `PopupInner.js:177` | `[[vShow, visible]]` 包着 `Align`，关闭时元素先被 `display: none` |
| 还原版 `vc-align/Align.js:57` | `if (element && isVisible(element)) alignElement(source, …)`：只检查**触发元素**可见，不检查弹层本身 |

所以弹层关闭后会在 `display: none`（零尺寸、`getBoundingClientRect` 全 0）的状态下被 dom-align 再定位一次。dom-align 按「目标文档坐标 − 当前文档坐标」改写行内 left/top，当前坐标是假的，结果就只取决于触发元素在整个文档里的位置：上方多 90px，top 就多 90px。下次打开时又走 measure → align，在弹层显示（`opacity` 为 0 直到 `motion`）之前重新对齐，所以这两个值从来不会被画出来。

实测（`tools/test/hidden-popup-offset-browser.test.mjs`，用 `hmrsfw-vue` 的 ant-design-vue UMD 包，与本页相同的 `size="large"`、宽 220px、`getPopupContainer: n => n.parentNode`，步骤同交互脚本：点开、选一项、重置）。同一页面只改上方空白块高度：

| 上方空白 | 打开时 style | 弹层顶 − 选择框底 | 关闭后 style | 再次打开 |
| --- | --- | --- | --- | --- |
| 0px | `left: 0px; top: 44px;` | 4px | `left: -439px; top: -655px; display: none;` | `left: 0px; top: 44px;` |
| 90px | `left: 0px; top: 44px;` | 4px | `left: -439px; top: -565px; display: none;` | `left: 0px; top: 44px;` |

打开时两边完全相同；关闭后 top 正好差 90px，与门槛里原版 −293 / 还原版 −383 同向同量；再次打开恢复。修正员第 2 轮的离线实测也是「两侧完整构建里下拉框打开时 `top:44px` 一致」（回执 `receipts/page.portal.talents.fair.webFair.list.json`，`integration` 分支 `feb86d9`）。

### 3. 改动

**hidden-popup-offset**（`kind: tree`）：元素同时满足下面两条时，去掉行内 style 里的 `left`、`top` 两条声明：

1. class 里有 vc-align 定位后才加上的方位类 `<前缀>-placement-<方位>`（正则 `^ant-[a-z]+(-[a-z]+)*-placement-[a-zA-Z]+$`，由 `PopupInner` 的 `onAlign` → `getClassNameFromAlign` 写入；如 `ant-select-dropdown-placement-bottomLeft`、`ant-tooltip-placement-top`、`ant-picker-dropdown-placement-bottomLeft`）；
2. 行内 style 有 `display: none`。

不变的东西：

- 这个元素 style 的其余声明（`min-width`、`width`、`display`、`z-index` 等）照常比较；
- 打开着的弹层（没有 `display: none`）位置照常比较；
- 没有方位类的元素不受影响，即使它也是 `display: none` 并带 left/top（基线里有 `rc-virtual-list-scrollbar`、百度地图 `BMap_noprint`、无 class 元素，见第 5 节）；
- `padding-left`、`margin-top` 之类只是名字里含 left/top 的声明照常比较；
- 弹层里的选项、文字、属性全部照常比较。

### 4. 为什么不算放宽

- **只规范化从不渲染的值。** `display: none` 的元素没有盒子，left/top 不影响任何像素；下次显示前 vc-trigger 一定重新对齐（第 2 节），旧值不会出现在屏幕上。
- **这两个值不是页面代码决定的。** 本页和 dictCode 都没给弹层传位置（第 1 节）；值由「触发元素在文档中的位置」和一次零尺寸测量算出，随外壳布局变化。门槛里还原版本来就没有外壳（外壳另有工单 `page.portal.talents.homeView`），这和已有做法一致：外壳的请求（`30-shell-requests-portal`）、外壳 toast（HM-250）、外壳画进截图的部分（HM-262、HM-253）都不算页面的差异。
- **阈值没变。** 像素阈值、请求判据、HTML 逐字比较都不变。
- **范围由确定的标记决定。** 只看 DOM 上的方位类和 `display: none`，不看位置、时机或数值大小。
- **不会让已通过的页面翻为失败。** 规则对两侧做同一个确定性变换，原来相同的两份 DOM 处理后仍然相同；204 份基线用 `main` 和本分支规则重算 `unstableKeys`，逐项相同。
