## HM-902：长 HTML 的易变掩码让 V8 报 `Regular expression too large`，门槛整页抛错

- 分支：`rule/hm-902-mask-match`（基于 `main` `329b669`），提交：
  1. `rule(gate-compare)`：`tools/gate/compare.mjs` 的 `maskRegex` 改为 `maskSegments` + `maskTest`；用例 `tools/test/compare-volatile-mask.test.mjs`；
  2. 本文。
- 合入 `main` 后，第 1 个提交 cherry-pick 到 `restore/fast-lane`（两条分支上 `tools/gate/compare.mjs` 逐字节相同），做法同 HM-876。
- 提出：裁定员；复核：两个非 Anthropic 家族的复核员。
- 来源：快速通道 HM-326（`page.portal.talents.index.jobRecommend`）、HM-329（`page.portal.talents.index.index`，重跑 14 次）、HM-376（`page.portal.zcyz.bigData.components.scrollList`）门槛都报 `[GATE] ERROR … Invalid regular expression`，没有结论。
- 不动的东西：归一化规则（`rules/compare/`）、像素阈值、请求判据、基线、HAR、公共库清单、交互脚本。掩码怎么从两次原版运行算出来（分词、LCS、50 个 hunk 上限、4e6 规模上限）也不变，只改掩码**怎么去匹配**还原版。

### 1. 根因：`maskRegex` 编出的正则太大，不是 `looseText`

两次原版运行在某个比对键上不一样时（时间戳、计数、轮播位置等），门槛用 `maskRegex` 从两次运行算一个掩码：两边相同的 token 原样保留，不同的地方各换成一个 `[\s\S]*?`，再编译成 `/^…$/` 去测还原版。列表、大屏页的 HTML 有 40–80 KB，hunk 前后的字面量也就有几十 KB。

实测（node 26）：只有字面量的正则多长都能编译；但和量词相邻的一段字面量超过约 32 K 字符，`test` 时 V8 就抛 `Invalid regular expression: /…/: Regular expression too large`。

| 字面量 + `[\s\S]*?` + 字面量 | 结果 |
| --- | --- |
| 100 + 20000 / 16000 + 16000 / 20000 + 20000 | 正常 |
| 100 + 33000 / 40000 + 100 | too large |

用三页的基线离线复现（`project()` 按还原版根节点的 class 取原版候选，然后调 `maskRegex`）：

| 页 | 键 | 两次原版长度 | 结果 |
| --- | --- | --- | --- |
| jobRecommend（HM-326） | `load.html`、`final.html` | 43705 / 43704 | too large |
| talents.index.index（HM-329） | `final.html`（根 `bgColor`） | 84040 / 84041 | too large |
| zcyz scrollList（HM-376） | `load.html` | 53622 / 53622 | too large |

异常出在 `compareRuns` 里，所以这三页在门槛目录下只有截图、没有 `report.json`，与门槛员看到的现象一致。

工单描述里怀疑的 `tools/interact.mjs:58` 的 `looseText`（门槛里是 `tools/gate/replay.mjs:129`）不是原因：它只编译交互脚本里的 `click` 文本，现有脚本里最长 5 个字符，这三页也没有 click 步骤。门槛员评论里「DOM 文本 / base64 被当作正则」指的其实是这个掩码。

### 2. 改动

`maskSegments` 用原来的步骤算掩码，返回 hunk 之间的字面段 `[S0, S1, …, Sk]`，不再拼正则字符串；`maskTest` 判断还原版 `r` 是否以 `S0` 开头、以 `Sk` 结尾、中间按顺序包含 `S1…S(k-1)`（每段取最左出现位置，段之间、段和结尾之间不重叠）。没有 hunk（k = 0）时就是 `r === S0`。

### 3. 为什么是等价写法，不算放宽

原正则是 `^` + 转义后的 `S0` + `[\s\S]*?` + `S1` + … + `Sk` + `$`，不带标志。`[\s\S]*?` 匹配任意串（含换行），惰性只影响匹配位置，不影响 `test` 的真假；转义后的字面量按 UTF-16 码元逐个匹配，和 `startsWith` / `indexOf` 一样；无 `m` 标志时 `$` 只匹配输入末尾。所以 `test(r)` 为真，当且仅当 `r` 能切成 `S0 · 任意 · S1 · … · 任意 · Sk`。只含 `*` 的通配匹配，中间段取最左出现是完备的：更靠后的出现只会给后面的段留更少的位置。两种写法接受的字符串集合相同，没有任何还原版在旧写法下判失败、新写法下判通过。旧写法抛错的地方，原来是整页没有结论，现在按同一个掩码给出结论（可能通过，也可能失败）。

证据：

- 用例 `same verdict as the old RegExp …`：把改前的 `maskRegex` 原样复制进测试，3000 组随机文本 / HTML（含正则元字符、换行、标签），每组 9 个候选串，`null` 与否和真假逐一相同。
- 用例 `long HTML …`：1000 行的列表页，旧正则 `test` 抛 too large；新写法只放过易变 hunk 里的差异，稳定行改一个字、少一行、末尾多一个元素都判不匹配。
- 用例 `compareRuns on a long page …`：同样规模的页走完整个 `compareRuns` 不抛错，易变部分豁免，稳定部分不同仍报 `load.html`。
- 离线全量对照（`$RESTORE_STATE` 下 204 份有两次运行的基线，每份试遍各阶段所有根节点 class 组合，候选为两次原版及各自改一个字符的副本；加上 172 份门槛 `report.json` 里真实的还原版投影）：建出 68 个掩码，共 310 次判定；旧写法能跑的 265 次，新旧结论 **0 处不同**；旧写法抛 too large 的 45 次分布在 6 页：上面三页，以及 `page.portal.talents.index.advertTop`、`page.portal.xjhm.bigData.statistics`、`page.portal.zcyz.bigData.components.pieRader`（还原版只要和两次原版都不同就会走到掩码，一样会抛错）。
