# 排障手册

每条按「现象 → 原因 → 处理」写，括号里是首次出现的任务号，详细过程可以去原单查。总的原则是：先判断问题出在**哪一层**（页面代码 / 公共库 / 比对器 / 测试资产 / 工具 / 环境），再找对应的处理入口。不要在页面里绕过别的层的问题，更不要为了通过去改规则。

## 门槛失败

### 连续 N 次同类门槛失败触发停止条件（HM-1175）
- **现象**：调度暂停派单，自动开一张 `[incident] 连续 5 次同类门槛失败：browser:root`。
- **原因**：先看这 N 次是不是**同一张任务**的同一条升级链。这次 5 次全是同一页，原因是交互脚本里有一步跳转到了别的路由，原版基线的最终状态根本不可比。属于测试资产问题，不是系统性故障。
- **处理**：同一张任务就退回重录（去掉跳转步骤），重新送门槛，然后 `tick.mjs resume`。真的是很多页同类失败，就按层归因：公共库的问题建升级单，比对器的问题建规则变更单。

### `browser:root` / `original page root not found`
- **原因**：取根节点的时候，要比对的组件不在 DOM 里。常见三种：组件要先点 tab 才挂载；弹窗用 `v-if`，脚本把它关掉了（HM-1170 / HM-1165）；脚本跳走了。
- **处理**：脚本停在目标状态（不点「关闭」），`recordPath` 带上能直接打开目标状态的参数。现有工具做不到「先交互再取根」的页，登记为回归例外，`kind: tool-gap`，并另开工具单。

### 门槛对每个加密接口都报失败
- **原因**：门槛员的环境里没有前端解密密钥（新建的 worktree 里没有 `.env.local`）。
- **处理**：门槛应该输出 `{"error":"crypto keys missing"}`，而不是逐页判失败。把密钥变量补进门槛员的环境文件，不要写进仓库。

### 门槛进程无输出、以 0 退出
- **原因**：Vite 依赖优化器还在打包，`server.close()` 就一直不返回。
- **处理**：门槛要保证最后总输出一行 JSON（`gate ended without a result`，退出码 2）。遇到无输出的情况，按门槛自身的错误处理，不推进。

### 运行时绘制的内容（二维码、canvas）像素差略超阈值
- **原因**：内容相同，画法不同（纠错等级、边距、版本选择、缩放）。
- **处理**：二选一，不要自己放宽阈值。一是还原侧对照原 bundle 的绘制参数修到像素一致；二是证明逐像素对齐不可行，走规则变更单（例如给该区域加掩码）。

### 交互脚本被误报「相对基线已变化」（HM-1132）
- **原因**：门槛读的脚本分支和录制员提交脚本的分支不一致（例如快速通道退场后，门槛从 `main` 读，而脚本提交在 `integration`）。
- **处理**：各种门槛模式统一读工具仓库的 `origin/integration`，整次运行固定在同一个提交上。

## 缺基线与录制循环

### 回归卡在 N 页缺基线，完成数停住（HM-1181）
- **现象**：全量回归返回 `PENDING record`，调度每轮「新派录制 0」，只是反复推进同一个结论。
- **原因**：集成回归遇到 `pending:record` 时不开录制，因为派录制会跳过账本里已有 `record` 值的页。另外还有几类具体情况：基线是用空脚本录的；录制单被取消后账本仍是 `blocked`；页面要造数才能录；需要人用有界面浏览器复查。
- **处理**：工具上，集成任务遇到 `pending:record` 时去掉例外页、给其余页重开录制，同一原因连续两次就交裁定员。数据上，能补的直接 `rerecord`，补不了的登记回归例外（附证据和解除条件），不让一页卡住几百页。

### 同一页反复 `pending:record`（HM-1131）
- **原因**：旧录制被当成「录制已完成」，任务每轮都被送回门槛。
- **处理**：等录制时记下 `waitRecordFrom`，只有之后完成的录制才算数。同一原因连续 `recordPendingLimit` 次就交裁定员，由裁定员判断是录制问题（`rerecord`）还是原站本身不稳定（登记已知差异）。

### 点名缺基线的是共享库或 npm 工单（HM-1124）
- **原因**：共享库和 npm 工单本来就不录制，等不到基线。
- **处理**：不开录制单、不进等待，直接交裁定员。

## 派单与调度

### 调度给 npm 共享库派了还原单（HM-1170）
- **现象**：`status: npm` 的工单被派了还原单，门槛 page 模式又要基线，只能一轮轮 `PENDING record → 裁定员`。
- **原因**：派单只看 `type`，没有看 `status`；快速通道退场后回到常规派单的那条路径也漏了这个判断。
- **处理**：派单统一经过 `isRestorable`，常规派单和快速通道两条路径都要过；已经关掉的这类任务，`advance` 和 `--regate` 不再重开。修复时要加测试，覆盖「连跑多轮 tick 都不重开」。

### 快速通道做过的入口包和共享组件又被派了单（HM-1068）
- **原因**：快速通道只在账本里记了整页任务，它做过的其他工单在 `queue/` 里仍是 `todo`。
- **处理**：关快速通道之前先跑 `node tools/tick.mjs fast-lane retire --app <产物工程> --dry-run` 预览，再正式执行。

### tick 写元数据超过 8KB，同一张任务每轮都失败（HM-1086）
- **现象**：`metadata exceeds the 8KB size limit`，任务停在 `backlog`、没有指派，每一轮都重试、报同一条异常。调度员每轮还会新建一张排障单。
- **原因**：平台的 8KB 上限算的是**一张单全部元数据的总和**。全量回归把 254 个页面 id 全写进了 `workOrders`。
- **处理**：超过 2KB 的 JSON 值压缩后写入（`z1:` 前缀，`encodeMeta` / `decodeMeta`）；长清单写进 `$RESTORE_STATE` 的明细文件，元数据只放计数和路径；`gate.<attempt>` 按剩余预算逐级截短。修好之前暂停定时自动化，避免每轮都开排障单。

### 同一规则线上积压很多张全量回归
- **原因**：每次规则变更都会开一张全量回归，但门槛每次都用当前的规则和当前的 integration。
- **处理**：只保留最新的一张，其余标为被它取代后关掉。代价是：如果最新那张失败，只会自动回退它对应的那一条规则。这一点要在单上写明，由人决定。

## 依赖与公共库

### 依赖版本与原包指纹不符（HM-1166）
- **现象**：页面行为有细微差别；清单、`package.json` 和原包三者版本不一致。
- **处理**：按 `05-deps-upgrade.md` 第 3 节逐版本核对，开升级单锁定正确版本；清单的版本号走规则变更单单独修正（HM-1170）。

### 公共库缺东西，页面里自己补了一份
- **原因**：还原员绕过了「公共库只有一个修改入口」这条规则。
- **处理**：合并时会被拒绝（页面单改到 `src/legacy|shared|api|utils`）。正确做法是写进 `needsFromSkeleton` → 建升级单 → 本页挂起 → 升级合并后自动重派。

## 环境与立项

### 第一次运行就失败：切 worktree 时目录还不是 git 仓库（广告机 G0）
- **处理**：先 `git init` 并做基线提交，再切 worktree 模式。

### 交付物是整理过的编译后 ESM 或旧 bundle 包装（桌面上屏 HM-899 / HM-901）
- **原因**：把「能回放」当成了「已还原」。
- **处理**：这不算完成。按 SKILL.md 的交付标准重做：标准工程、可编辑的 SFC、新源码真正构建，旧包只用来比对。

### 多台机器的凭据和路径反复出问题（HM-212）
- **处理**：一台稳定的机器优于多台不稳定的机器。停用出问题的机器，名册里把它标为 `enabled: false`；它领着的工单用 `claims reclaim` 接管。并发按单机内存实测来定，不要硬调大。

### 任务元数据键名被拒
- **原因**：平台的 metadata 键只接受 `^[a-zA-Z_][a-zA-Z0-9_.-]{0,63}$`，智能体名字里有 `@` 和中文。
- **处理**：键名用智能体 id，例如 `review.<agent id>`。
