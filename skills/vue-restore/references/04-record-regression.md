# 录制、基线与回归

门槛只跑还原版这一侧。原版那一侧的 DOM、文本、截图和请求序列，都由录制阶段缓存成基线。所以**没有基线的页面过不了门槛**，录制要始终领先于还原。

## 1. 交互脚本

`tests/interact/<工单id>.json`，格式是 `[{"fill":[placeholder,value]} | {"click":text} | {"clickSel":css,"optional":bool} | {"wait":ms}]`。

- 读原 chunk 找出页面上的交互：查询、重置、翻页、表单校验、提交、弹窗、tab 切换。优先覆盖会发请求的操作，每页 3–8 步。
- 表单页、操作页必须写交互脚本；其他页面按项目默认值抽检。
- 填写值用明显的测试值（`测试`、`Tst-0001`），不要用真实姓名、手机号、证件号。
- 回放时不稳定的步骤（两次结果不同）删掉再重录。
- **要比对的状态必须在取根时还在**：弹窗、抽屉用 `v-if` 挂载时，关掉它根节点就没了。脚本停在弹窗打开的状态，不要点「关闭」。
- 不要让脚本跳转到别的路由。跳走以后，最终状态的根节点就不可比了。
- 录制前读工单的 `recordNotes`。路由参数、要先点哪个 tab、哪些按钮不能点，都写在 `tools/record-path-overrides.json` 里，每条都附原 chunk 证据。

## 2. 录制

```bash
node tools/record-page.mjs <工单id>     # 只在持有登录态的机器上运行，只访问配置里的测试域名
```

它会依次做这些事：切到工单身份 → 在测试站真实执行一遍并录 HAR → 用 HAR 回放原版两次，写出基线 `$RESTORE_STATE/baseline/<id>/`（两次不一致的比较项记为 `unstable`，比对时不比这些位置） → 采集原版 JS 覆盖率 → 把交互脚本提交到工具仓库的 `integration` 分支（只提交脚本，不提交 HAR）。

- **写接口默认拦截**：名单（`record-write-denylist.json`）里的提交、新增、删除、报名等请求不发到测试站，统一返回固定的成功响应。名单之外的 POST 请求会出现在 `warnings` 里，需要人补进名单。全部录完后，由人重置一次测试环境。
- 登录态失效时输出 `blocked: login-expired`，没有登录态时输出 `need-login`，这两种都要找人重新登录。身份切不过去输出 `need-role`，身份没判定输出 `need-role-decision`。都不要猜。
- 同一个账号的不同身份共用一把账号锁：同身份可以并发，不同身份要排队。
- 覆盖率太低（低于配置的 `coverage.minFunction` / `minBlock`）时，用 `coverage.mjs report <id>` 查看未覆盖的部分，补交互；要造数据才能覆盖的，记进造数清单（`coverage.mjs datareq`），等人统一造数。

**重录**（`tick.mjs rerecord <工单>`）：基线是用空脚本或旧脚本录的、脚本或 HAR 在基线之后有变化、录制路由不对，都要重录。旧录制不算数，只有之后完成的录制才算「录制已完成」。

## 3. 三种豁免（性质不同，别混用）

| | 已知差异 known-diff | 回归例外 regression-exceptions | 规则变更单 |
| --- | --- | --- | --- |
| 用途 | **某一页**的差异来自原代码本身或原站不稳定，还原版保留原行为 | **某一页**现在拿不到可用基线（要人造数、要人用有界面浏览器复查、现有工具录不了），先不让它卡住整批回归 | **比对器**把等价写法判成不同，对所有页面生效 |
| 谁登记 | 只有裁定员（`known-diff.mjs add`） | 裁定员，提交 PR 修改 `tools/regression-exceptions.json` | 裁定员提出，两个不同家族的复核员批准 |
| 证据 | 原 chunk 位置 + 原因 + 豁免哪一项（粗：`load.overlay`；细：两侧片段替换成同一个占位符） | `kind`、`why`、`evidence`（原 chunk 位置）、`unblock`（什么条件下删除这条） | 原版与还原版的对照、等价性论证、影响面 |
| 算不算通过 | 被豁免项不判失败，其他照常比 | **不算通过，不计完成**，只是不进回归页集 | 合并后全量回归 |

规则变更单的要求：

- 只认**等价写法的规范化**（例如属性顺序、空注释节点、相对和绝对资源路径解析到同一个文件）。放宽阈值（像素比例、请求序列允许的差异）一律不行。
- 每条规则一个文件（`rules/compare/NN-<id>.json`），一个提交，可以单独 `git revert`。
- 证据写在 `docs/rule-changes/<任务号>.md`，包括原 chunk 证据、为什么不算放宽、影响面。
- 运行 `tick.mjs open-rule-review <分支>`，派给两个与裁定员（提出者）不同家族的复核员。两人都同意才合并到工具仓库 `main`；第 2 轮仍有人否决，就升级给人。
- 合并后自动建一张 `rule-regression`（全量回归），失败就自动回退。

## 4. 回归

| 回归类型 | 触发 | 范围 |
| --- | --- | --- |
| 集成回归 `regression` | `integration` 每新合入 N 单（默认 20），或者空闲时 | 全部已通过页面；通过就把 `main` 快进到该提交，失败就二分（`bisect`）找到引起问题的合并并回退 |
| 公共库回归 `lib-regression` | 入口包、共享组件、升级单合并后 | 通过 `deps` 反向索引找到的依赖页面；失败就回退这次公共库合并，不改页面 |
| 规则回归 `rule-regression` | 规则变更合并后 | 全部已通过页面；失败就回退规则 |
| 集成门槛 `integration-gate` | 入口包和共享组件全部合入后 | 所有页面用 integration 模式跑（不顶替） |

- 回归跑的是**当前规则 + 当前 integration**。所以同一条规则线上排着的多张全量回归，测的其实是同一件事，保留最新的一张，其余标为被它取代后关掉，不要跑 N 遍整套回归。
- 回归返回 `pending:record` 时：去掉例外页，给其余缺基线的页开录制或重开录制，等录完再重跑门槛。同一原因连续两次，就交给裁定员。不要每轮都推进同一个结论。
- 已经 `done` 的页面在之后的回归或审计里失败，同样重开处理。
