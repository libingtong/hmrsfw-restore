# 依赖与公共库升级

## 1. 公共库是唯一的

每个应用的公共库由以下几部分组成：`src/legacy`（入口导出）、`src/shared`（共享组件）、`src/api`（接口模块）、`src/utils`、全局组件与指令，以及锁定版本的 npm 依赖。不同应用的框架版本不同时，各自一套，不跨应用共用。

`registry/<app>.json` 是唯一事实来源：原包里的每个公共符号都映射到一个固定的源码位置（`path` + `export` + `status: restored|reserved|npm|ignore` + `owner`）。

- **先占位再还原**：还没还原的模块也先分配好路径和名字（`reserved`）。页面按清单导入，门槛临时顶替。
- **同名不同接口**：按 URL 和方法逐个核对后再分配，不能合并成一个。
- 清单从现有源码反推生成（`registry.mjs`），可以重跑，`--check` 校验结果一致。改名后用 `refresh-names.mjs` 只刷新工单的 maps。
- 清单和比对、归一化规则一样，改动走规则变更单（`docs/pipeline.md` 第十三节第 4 条、第十五节第 3 条；见 `04-record-regression.md`），即使只改一个版本号（HM-1170）。

## 2. 还原 package.json

1. 列出原包打进来的全部第三方库：`vendor` chunk、`modules` 段、入口里的 npm 符号、超大 chunk 里内联的 SDK。
2. 每个库按下一节的方法锁定**精确版本**，写进产物工程的 `package.json` 和锁文件。
3. 打包进来的 npm 组件库（例如滚动、数字动画组件）用 npm 依赖代替，工单 `status: npm`，**不出还原单**。
4. 原包里没有官方 npm 包的插件，标「待核对」，交裁定员决定是还原成源码还是找替代包。
5. 页面工单不能新增依赖。依赖只能由入口包单、共享组件单或升级单修改。
6. 一个仓库里有多个应用、各自需要不同版本时，拆成每个应用一份 `package.json`。

## 3. 按原包指纹核对版本

版本号写错是常见事故：清单、`package.json` 和原包三者不一致，页面行为就会有细微差别。核对步骤：

1. **先找直接证据**：banner 注释、`version` 常量、`majorVersion/minorVersion` 字段。
2. **没有直接证据时，逐版本比对产物**：从 npm 下载候选版本的 `dist/*.es.js`，和原 chunk 对照**行为特征**（例如某个侦听器里有没有调用回调）和**编译特征**（例如对象展开是 esbuild 降级出来的 `__spreadValues`，还是原生的 `...`）。
3. 找到「与原 chunk 一致」的版本区间，取区间里的一个版本锁定。区间内各版本产物逐字相同时，说明一下即可。
4. 证据写成表格：「特征 | 版本 A | 版本 B | 原 chunk」，引用原 chunk 的 `文件:行:列`。
5. 三处同步：产物工程 `package.json` + 锁文件、`registry/<app>.json` 的 `npm` 段、`project-notes.md`。

用这个方法在实际项目里纠正过一个组件库：清单写的是 1.4.2，原包是 1.4.0。依据是 1.4.1 起 `finished` 侦听会调用回调，展开也改成了原生写法。

## 4. 公共库升级单（`kind=upgrade`）

还原员在回执的 `needsFromSkeleton` 里写明公共库缺什么或有错，或者裁定员判定问题出在公共库，就会建升级单（`tick.mjs open-upgrade`）。

- 升级单由强模型（核心还原员）来做，只能改公共库文件、`public/`、`package.json` 和锁文件，**不能改页面**（`src/views/**`）。同一个文件同一时间只能有一张单在改，按清单的 `owner` 加锁。
- 门槛用 `--mode upgrade`：先判改动范围（和调度器合并时用同一个判定函数），再编译改动的文件、跑零引用和个人信息检查，然后整站构建，最后对依赖改动文件的已通过页面跑回归。
- 合并后：被挂起的页面自动重派；如果有快速通道分支，把这次升级同步过去（同步冲突时快速通道页保持挂起，等人工合入）。
- 交付：运行 `node tools/handoff.mjs <任务id>`。
